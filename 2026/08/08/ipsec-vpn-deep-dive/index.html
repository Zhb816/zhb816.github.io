IPSec VPN 深度解析——IKEv2、ESP、NAT 穿越与高可用

IPSec 是企业 VPN 的事实标准，不管是站点到站点（Site-to-Site）还是远程接入（Remote Access），底层几乎都是 IPSec。但很多人只会照着模板配，对 IKE 协商、ESP 封装、NAT 穿越这些原理一知半解，出了问题只能抓瞎。这篇文章把 IPSec 从里到外拆一遍。

一、IPSec 协议族概览

IPSec 不是一个协议，是一组协议的集合：

核心概念：SA（Security Association，安全关联）

SA 是 IPSec 的基础，它定义了”用什么协议、什么加密算法、什么密钥、封装模式”来保护流量。SA 是单向的，所以一条双向通信需要两个 SA（一个入方向、一个出方向）。

SA 由 SPI（Security Parameter Index）唯一标识，SPI 是一个 32 位的数字，放在 ESP/AH 头里，接收方用 SPI 查找对应的 SA。

二、IKE 协商——密钥是怎么来的

IPSec 用对称加密（AES）保护数据，但对称密钥需要安全地分发。IKE 就是用来协商密钥和建立 SA 的协议。

2.1 IKEv1：两阶段协商

IKEv1 分两个阶段：

第一阶段（Main Mode / Aggressive Mode）：建立 IKE SA（也叫 ISAKMP SA），这是一个控制通道，用来保护后续的协商流量。

Main Mode 有 6 条消息：

  1. 发起方 → 响应方：提议（加密算法、哈希算法、认证方式、DH 组）
  2. 响应方 → 发起方：接受提议
  3. 发起方 → 响应方：DH 公钥 + Nonce（随机数）
  4. 响应方 → 发起方：DH 公钥 + Nonce
  5. 发起方 → 响应方：身份信息（IP/域名）+ 认证（预共享密钥/证书签名），加密
  6. 响应方 → 发起方：身份信息 + 认证，加密

前 4 条消息明文，后 2 条加密（用 DH 协商出的密钥加密）。

Aggressive Mode 只有 3 条消息，把身份信息在第 1 条就发了（明文），速度快但安全性差，不推荐。

第一阶段协商完成后，双方有了：

  • 共享密钥（通过 DH 算法计算得出，DH 是 Diffie-Hellman 密钥交换）
  • IKE SA（保护后续协商的加密通道）

第二阶段（Quick Mode）：建立 IPSec SA（数据通道），用来保护实际业务流量。

Quick Mode 有 3 条消息（都在 IKE SA 的保护下，加密传输）：

  1. 发起方 → 响应方：提议（ESP/AH、加密算法、认证算法、感兴趣流）+ Nonce
  2. 响应方 → 发起方：接受提议 + Nonce
  3. 发起方 → 响应方：确认

第二阶段完成后，建立了两个方向的 IPSec SA，业务流量可以通过 ESP 加密传输了。

2.2 IKEv2：更简单、更安全、更快

IKEv2 只有一个阶段，4 条消息（IKE_SA_INIT + IKE_AUTH）：

  1. IKE_SA_INIT 请求：发起方 → 响应方，包含 IKE 提议、DH 公钥、Nonce
  2. IKE_SA_INIT 响应：响应方 → 发起方，包含接受的提议、DH 公钥、Nonce
    • 到这里，双方已经通过 DH 计算出共享密钥
  3. IKE_AUTH 请求：发起方 → 响应方，包含身份、认证（证书/预共享密钥/EAP）、第一个 CHILD_SA 的提议，全部加密
  4. IKE_AUTH 响应：响应方 → 发起方，包含身份、认证、CHILD_SA 确认，全部加密

IKEv2 相比 IKEv1 的优势：

  • 消息更少：4 条 vs 9 条（Main Mode 6 + Quick Mode 3），建立更快
  • 内置 DPD（Dead Peer Detection）：IKEv1 需要额外配置，IKEv2 原生支持
  • 支持 MOBIKE：移动端网络切换（WiFi→4G）时，IP 变了但隧道不中断
  • 支持 EAP 认证：可以和 RADIUS、LDAP 集成，做远程接入的用户名密码认证
  • 更安全的密钥派生：用 PRF（伪随机函数）派生多个密钥，每个用途的密钥独立
  • NAT 穿越原生支持：IKEv1 的 NAT-T 是扩展，IKEv2 原生支持

2.3 DH 算法——密钥交换的核心

DH（Diffie-Hellman）密钥交换是 IKE 的核心，它让双方在不安全的信道上协商出共享密钥，而不需要直接传输密钥。

原理（简化版）：

  1. 双方约定一个大素数 p 和一个生成元 g
  2. 发起方生成私钥 a，计算公钥 A = g^a mod p，发给响应方
  3. 响应方生成私钥 b，计算公钥 B = g^b mod p，发给发起方
  4. 发起方计算共享密钥 = B^a mod p = (g^b)^a mod p = g^(ab) mod p
  5. 响应方计算共享密钥 = A^b mod p = (g^a)^b mod p = g^(ab) mod p
  6. 双方得到相同的共享密钥 g^(ab) mod p

攻击者即使截获了 A 和 B，没有 a 或 b，也无法计算出共享密钥（离散对数难题）。

DH 组的选择：

  • Group 1：768 位，不安全，已废弃
  • Group 2：1024 位，不推荐
  • Group 5：1536 位，勉强可用
  • Group 14：2048 位，推荐最低标准
  • Group 19：256 位 ECP（椭圆曲线），推荐，速度快
  • Group 20：384 位 ECP，高安全场景
  • Group 21：521 位 ECP，最高安全

椭圆曲线 DH（ECDH）比传统 DH 用更短的密钥达到相同的安全强度，计算更快，推荐使用 Group 19/20。

三、ESP——数据是怎么加密的

ESP（Encapsulating Security Payload）是 IPSec 数据面的核心协议，负责加密和认证。

3.1 ESP 报文格式

  • SPI：32 位，标识 SA
  • 序列号：32 位，防重放攻击（接收方维护一个滑动窗口，重复或过旧的序列号丢弃）
  • 载荷数据：加密的原始 IP 报文（隧道模式）或传输层报文（传输模式）
  • 填充：加密算法要求明文长度是块大小的整数倍，需要填充
  • 填充长度：填充了多少字节
  • 下一个头部：原始报文的协议类型（4=IP-in-IP, 6=TCP, 17=UDP）
  • ICV：完整性校验值，对整个 ESP 报文计算认证（HMAC-SHA1/SHA256），防篡改

3.2 隧道模式 vs 传输模式

传输模式（Transport Mode）：只加密传输层内容，原始 IP 头保留。

  • 优点：开销小（不需要额外 IP 头）
  • 缺点：原始 IP 头明文，能看到源和目的 IP；只能保护端到端通信，不能用于 VPN 网关
  • 适用场景：主机到主机的端到端加密（比如两台服务器之间直接加密）

隧道模式（Tunnel Mode）：加密整个原始 IP 报文，外面再加一个新 IP 头。

  • 优点：原始 IP 头加密，隐藏内部网络拓扑；可以用于 VPN 网关（网关之间建立隧道，内部主机流量通过隧道转发）
  • 缺点：开销大（额外 20 字节 IP 头 + ESP 头/尾/ICV，总共约 50-60 字节）
  • 适用场景：Site-to-Site VPN、远程接入 VPN（主流都是隧道模式）

3.3 加密和认证算法

加密算法（对称加密，加密数据）：

  • DES：56 位，不安全，已废弃
  • 3DES：168 位，不推荐（慢且有安全问题）
  • AES-128：推荐，性能和安全的平衡
  • AES-256：高安全场景
  • AES-GCM：认证加密（AEAD），加密和认证一次完成，性能好，推荐
  • ChaCha20-Poly1305：移动设备上性能好

认证算法（完整性校验，防篡改）：

  • MD5：不安全，已废弃
  • SHA1：不推荐（碰撞攻击）
  • SHA2-256：推荐
  • SHA2-384/512：高安全场景
  • AES-GCM/ChaCha20-Poly1305：自带认证，不需要单独的认证算法

推荐组合：AES-256-GCM + ECP Group 20 + SHA2-384，这是目前的最佳实践。

四、NAT 穿越（NAT-T）

IPSec 在 NAT 环境下会遇到问题：

  1. ESP 协议没有端口号：ESP 是 IP 协议号 50，没有 TCP/UDP 端口，NAT 设备无法做端口转换（PAT），多个内网主机不能共用一个公网 IP 做 IPSec
  2. AH 认证整个 IP 头：NAT 修改 IP 头后，AH 的认证会失败（所以 AH 完全不支持 NAT）
  3. IKE 协商中的 IP 地址：IKE 载荷里包含了对端 IP，NAT 修改后会导致认证失败

NAT-T 的解决方案

NAT-T 把 ESP 报文封装在 UDP 里（端口 4500），这样 NAT 设备就能像处理普通 UDP 一样处理 ESP 报文：

NAT-T 的工作流程：

  1. NAT 发现：IKE 协商时，双方发送 NAT-D 载荷（包含对端 IP 和端口的哈希），如果发现中间有 NAT 设备（哈希不匹配），就自动启用 NAT-T
  2. 端口切换：IKE 协商从 UDP 500 切换到 UDP 4500（因为 500 端口在某些 NAT 设备上有特殊处理）
  3. ESP 封装：数据面的 ESP 报文封装在 UDP 4500 里传输
  4. 保活报文：NAT 会话有超时时间，IKE 发送 NAT-T Keepalive 报文（1 字节的 UDP 报文）保持 NAT 会话不超时

NAT-T 的限制

  1. 只能有一个 NAT 设备在路径上：如果有多层 NAT（运营商 NAT + 家用路由器 NAT），可能会有问题
  2. NAT 设备不能改变 IKE 端口：如果 NAT 设备把 UDP 500 改成其他端口，IKE 会失败（所以很多设备强制用 4500）
  3. AH 不支持 NAT-T：AH 认证整个 IP 头，NAT 修改后认证必然失败，所以 AH 在 NAT 环境下完全不可用
  4. MTU 更小：NAT-T 额外加了 UDP 头（8 字节），有效 MTU 进一步减小，需要调小 MSS

五、IPSec VPN 的高可用

生产环境里 IPSec VPN 不能是单点，需要高可用设计。

5.1 双机热备

VPN 网关双机部署，用 VRRP/HSRP 做网关冗余，主设备故障时备设备接管。

问题：IPSec SA 是在主设备上建立的，主设备故障后，备设备没有 SA，隧道需要重新协商，业务中断时间长（IKE 协商要几秒）。

解决方案：SA 同步（Stateful Failover），主设备把 IKE SA 和 IPSec SA 实时同步到备设备，故障切换时备设备直接用同步的 SA，不需要重新协商，业务中断时间 < 1 秒。

5.2 多隧道负载分担

建立多条 IPSec 隧道（不同的对端 IP 或不同的加密域），用路由协议（OSPF/BGP）或策略路由做负载分担。一条隧道故障时，流量自动切到另一条。

5.3 DPD（Dead Peer Detection）

DPD 定时发送 Hello 报文检测对端是否存活，如果连续几次没有收到回应，认为对端故障，删除 SA 并重新协商。

IKEv2 原生支持 DPD，IKEv1 需要额外配置。

DPD 配置要点：

  • 检测间隔不要太短（建议 10-30 秒），否则会增加不必要的流量
  • 重试次数 3-5 次
  • 检测到故障后要能自动重建隧道

5.4 隧道保活

有些运营商的 NAT 或防火墙会超时删除空闲会话，需要配置隧道保活：

  • IKE Keepalive：IKE 层面的保活报文
  • NAT-T Keepalive：NAT 环境下的 1 字节 UDP 保活
  • 业务层面保活：有些应用自己有心跳，能保持隧道活跃
  • 永久隧道（Always-On）：配置感兴趣流为 any，隧道永久保持，不因为没有流量而超时

六、常见故障排查

6.1 隧道建立不起来

排查顺序：

  1. 连通性：ping 对端公网 IP，通不通？
  2. 端口：UDP 500 和 4500 有没有被中间防火墙拦？
  3. IKE 提议：两边的加密算法、哈希算法、DH 组、认证方式是否一致？
  4. 认证信息：预共享密钥是否一致？证书是否有效（过期、吊销、信任链）？
  5. 身份信息：IKE 协商的身份（IP/域名/证书 DN）是否匹配？
  6. NAT 环境：有没有 NAT？NAT-T 是否启用？
  7. 抓包： 看协商到哪一步停了，是 IKE_SA_INIT 没回应，还是 IKE_AUTH 失败。

6.2 隧道建立了但业务不通

  1. 感兴趣流（ACL）：两边的加密域是否匹配？发起方的源=对端的目的，发起方的目的=对端的源，要镜像对称。
  2. 路由：到对端内网的路由是否指向隧道接口？
  3. NAT：有没有 NAT 把内网地址转换了？IPSec 感兴趣流要在 NAT 之前匹配，需要配置 NAT 豁免（NAT Exemption）。
  4. 防火墙策略：隧道接口到内网接口之间有没有安全策略放行？
  5. MTU/MSS：大包不通小包通，基本就是 MTU 问题，调小 MSS。
  6. SA 不匹配：两边的 SA 提议（ESP 加密/认证算法）是否一致？

6.3 隧道时断时续

  1. DPD 配置：DPD 太敏感，网络轻微抖动就认为对端故障，删除 SA。调大 DPD 间隔和重试次数。
  2. NAT 会话超时：NAT 设备超时删除会话，配置 NAT-T Keepalive。
  3. 链路质量差：丢包导致 IKE 协商失败或 DPD 超时，检查 Underlay 链路质量。
  4. SA 生命周期不匹配：两边 SA 生命周期差太多，一边过期重建时另一边还在用旧 SA，导致短暂中断。尽量让两边生命周期一致。

七、IPSec VPN 设计最佳实践

  1. 用 IKEv2，不用 IKEv1：IKEv2 更安全、更快、功能更多，除非对端设备太老不支持
  2. 用证书认证，不用预共享密钥：预共享密钥管理困难（每个隧道一个密钥，多了根本管不过来），证书可以集中管理、自动轮换
  3. 用 AES-GCM，不用 AES-CBC + HMAC：GCM 是认证加密，一次完成加密和认证，性能更好，安全性更高
  4. 用 ECP DH 组（Group 19/20）：比传统 DH 更快更安全
  5. 配置 PFS（Perfect Forward Secrecy）：第二阶段协商时也做 DH 交换，即使长期密钥泄露，历史会话密钥也无法被破解
  6. 合理配置 SA 生命周期：IKE SA 8-24 小时，IPSec SA 1-8 小时，不要太短（频繁协商增加开销）也不要太长（密钥用太久不安全）
  7. 配置 DPD 和自动重连：确保故障后能自动恢复
  8. 调小 MSS：IPSec 隧道的 MSS 建议设为 1360（MTU 1400 - 40），NAT-T 环境再减 8（1352）
  9. 监控隧道状态：用 SNMP 或日志监控隧道 Up/Down，及时发现故障
  10. 文档化：每个隧道的对端、加密域、算法、密钥位置都要记录，运维时能快速定位

八、总结

IPSec VPN 的核心就三层：

  1. IKE 协商：用 DH 算法安全地协商密钥，建立 SA（控制面）
  2. ESP 封装：用对称加密加密业务流量，隧道模式隐藏内部拓扑（数据面）
  3. NAT-T 和高可用：解决 NAT 环境下的兼容性和生产环境的可靠性

理解了这三层，再看任何厂商的 IPSec 配置，本质都是在配置这三层的参数。排查故障时也按这个顺序来：先看 IKE 协商通不通（控制面），再看 ESP 封装对不对（数据面），最后看 NAT 和路由（环境因素）。
