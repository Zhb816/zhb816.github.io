Kubernetes 网络底层原理——从 Pod IP 到 Service 全链路解析

Kubernetes 的网络一直是最容易让人困惑的部分。Pod IP 是怎么来的？Service 为什么能负载均衡？kube-proxy 到底干了什么？这篇文章从底层原理出发，把一个数据包从 Pod 发出到到达目标的完整路径走一遍。

一、Kubernetes 网络模型

Kubernetes 对网络有四个基本要求（CNI 规范）：

  1. Pod 之间可以直接通信，不需要 NAT
  2. Node 上的进程可以和 Pod 通信（包括 Pod 的 localhost）
  3. 每个 Pod 有独立的 IP，Pod 内的容器共享网络命名空间（localhost）
  4. 不关心容器怎么分配 IP，只要满足上面三条就行

核心思想：IP 是 Pod 的，不是容器的。一个 Pod 里的多个容器共享同一个 network namespace，共享同一个 IP、同一个端口空间。

二、Pod 网络是怎么通的——CNI 详解

2.1 网络命名空间

每个 Pod 有自己独立的 network namespace，里面有：

  • 独立的网络栈（IP、路由表、iptables）
  • 独立的网卡（lo + 一个 eth0）
  • 独立的端口空间

Pod 里看到的 eth0，实际上是一对 veth pair 的一端，另一端在宿主机的 root namespace 里，通常接在一个网桥上（比如 docker0、cni0）。

2.2 CNI 插件做了什么

CNI（Container Network Interface）是一个规范，定义了容器运行时和网络插件之间的接口。当 kubelet 创建 Pod 时，会调用 CNI 插件来配置网络。

以 Flannel（vxlan 模式）为例，CNI 插件干这些事：

  1. 创建 veth pair：一端放进 Pod 的 network namespace，命名为 eth0；另一端留在宿主机，命名为 vethXXX
  2. 分配 IP：从节点的 Pod CIDR（比如 10.244.1.0/24）里分配一个 IP 给 Pod 的 eth0
  3. 配置路由：在 Pod 里设置默认路由指向 veth pair 的对端（网关）
  4. 把 veth 接到网桥：宿主机端的 veth 接到 cni0 网桥上
  5. 配置 ARP 和 FDB：vxlan 模式下需要配置 ARP 表和 FDB（转发数据库）表项，让跨节点的流量能找到对端

2.3 跨节点通信——以 Flannel VXLAN 为例

Pod A（10.244.1.5，Node1）要访问 Pod B（10.244.2.8，Node2）：

  1. Pod A 的报文：源 IP 10.244.1.5，目的 IP 10.244.2.8
  2. 报文通过 veth pair 到宿主机 Node1 的 cni0 网桥
  3. Node1 查路由表：10.244.2.0/24 下一跳是 flannel.1（vxlan 接口）
  4. 报文进入 flannel.1，进行 VXLAN 封装：
    • 外层：源 IP Node1(192.168.1.10)，目的 IP Node2(192.168.1.20)，UDP 8472
    • 内层：源 IP 10.244.1.5，目的 IP 10.244.2.8
  5. 封装后的报文通过宿主机物理网卡发出，经过 Underlay 网络到达 Node2
  6. Node2 的 flannel.1 收到报文，解封装，取出内层报文
  7. Node2 查路由：10.244.2.8 在本地 cni0 网段
  8. 报文通过 cni0 网桥 → veth pair → Pod B 的 eth0

关键：跨节点通信靠的是 Overlay 隧道（VXLAN），Pod IP 对 Underlay 网络是不可见的。

2.4 主流 CNI 对比

CNI 模式 性能 功能 适用场景
Flannel VXLAN/host-gw 中 基础网络 简单集群
Calico BGP/IPIP 高 网络策略 需要NetworkPolicy
Cilium eBPF 极高 策略+可观测 大规模/高性能
Weave VXLAN 中 简单 小集群

三、Service——kube-proxy 的三种模式

Pod IP 是不稳定的（Pod 重建后 IP 会变），Service 提供了一个稳定的虚拟 IP（ClusterIP），作为一组 Pod 的负载均衡入口。

Service 的实现靠 kube-proxy，它有三种工作模式：

3.1 userspace 模式（已废弃）

最早的模式，kube-proxy 在用户态监听一个端口，报文先到 kube-proxy，再由它转发到后端 Pod。性能差，因为每次转发都要经过用户态和内核态的切换。

3.2 iptables 模式（默认）

kube-proxy 监听 Service 和 Endpoint 的变化，动态生成 iptables 规则。报文在内核态通过 iptables 的 DNAT 完成转发，不经过 kube-proxy 进程。

iptables 模式的问题：

  • 规则线性匹配：Service 多了以后，iptables 规则数量爆炸，匹配延迟增加
  • 不支持连接级别的负载均衡算法：只能随机，不支持轮询、最少连接
  • 更新延迟：每次 Endpoint 变化都要全量刷新 iptables 规则，大规模集群里很慢

3.3 IPVS 模式

IPVS（IP Virtual Server）是 Linux 内核里的 L4 负载均衡器，专门做四层负载均衡，比 iptables 高效得多。

IPVS 模式下，kube-proxy 用 IPVS 代替 iptables 做 Service 的负载均衡，iptables 只用来做 SNAT 和一些基础规则。

优势：

  • O(1) 查找：IPVS 用哈希表存储规则，查找时间不随规则数量增长
  • 多种调度算法：轮询（rr）、加权轮询（wrr）、最少连接（lc）、源地址哈希（sh）、目的地址哈希（dh）、最短预期延迟（sed）、永不排队（nq）
  • 更新效率高：增量更新，不需要全量刷新

3.4 eBPF 模式（Cilium）

Cilium 用 eBPF 完全替代 kube-proxy，在 XDP 和 TC 层做 Service 的负载均衡，性能比 IPVS 还高，而且支持更丰富的策略和可观测性。

四、完整报文路径走查

4.1 Pod 访问同节点的另一个 Pod

Pod A(10.244.1.5) → Pod B(10.244.1.6)，都在 Node1：

  1. Pod A 发出报文，目的 IP 10.244.1.6
  2. Pod A 的路由表：默认网关是 10.244.1.1（cni0），报文发到 veth pair
  3. 报文到 Node1 的 cni0 网桥
  4. cni0 网桥查 MAC 地址表，找到 10.244.1.6 对应的 veth 接口
  5. 报文通过 veth pair 进入 Pod B 的 network namespace
  6. Pod B 收到报文

全程不经过宿主机协议栈的路由，只在网桥二层转发，非常快。

4.2 Pod 访问 Service（ClusterIP）

Pod A(10.244.1.5) → nginx Service(10.96.0.100:80)：

  1. Pod A 发出报文，目的 IP 10.96.0.100，目的端口 80
  2. 报文通过 veth pair 到 Node1 的 cni0，再进入宿主机协议栈
  3. 报文进入 iptables PREROUTING 链 → KUBE-SERVICES
  4. 匹配到 ClusterIP 10.96.0.100，跳转到 KUBE-SVC-nginx
  5. 随机选择一个后端，比如 10.244.2.8（在 Node2）
  6. DNAT：目的 IP 从 10.96.0.100 改成 10.244.2.8
  7. Node1 查路由：10.244.2.0/24 走 flannel.1（VXLAN 隧道）
  8. VXLAN 封装后发到 Node2
  9. Node2 解封装，报文到 cni0，再到 Pod(10.244.2.8)
  10. 回程报文：源 IP 10.244.2.8，目的 IP 10.244.1.5（DNAT 已经改了目的地址，conntrack 记录了这个连接）
  11. 回程通过 VXLAN 到 Node1，conntrack 做反向 NAT（源 IP 改回 10.96.0.100）
  12. 报文回到 Pod A

关键点：DNAT 是在第一个包经过时做的，后续包靠 conntrack 自动完成 NAT，不需要再匹配 iptables 规则。

4.3 外部访问 Service（NodePort）

NodePort 模式下，Service 会在每个节点上开放一个端口（默认 30000-32767），外部访问 节点IP:NodePort 就能访问到 Service。

报文路径：

  1. 外部客户端 → Node1:30080
  2. Node1 的 iptables PREROUTING 匹配到 NodePort 规则，DNAT 到某个后端 Pod
  3. 如果后端 Pod 在 Node2，报文通过 VXLAN 隧道转发到 Node2
  4. 回程报文从 Node2 直接回到客户端（源 IP 是 Pod IP？不对，需要 SNAT）

这里有个问题：如果后端 Pod 在其他节点，回程报文的源 IP 是 Pod IP，客户端不认。所以 NodePort 默认会做 SNAT（源地址伪装），把源 IP 改成节点 IP，这样回程报文能回到正确的节点。

可以通过 externalTrafficPolicy: Local 关闭 SNAT，但这样只有本地有后端 Pod 的节点才能处理流量，其他节点会丢包。好处是能保留客户端真实 IP。

五、NetworkPolicy——Pod 级防火墙

默认情况下，Kubernetes 里所有 Pod 之间是互通的。NetworkPolicy 可以限制 Pod 之间的访问，相当于 Pod 级别的防火墙。

NetworkPolicy 的实现依赖 CNI 插件，Flannel 不支持，Calico 和 Cilium 支持。

Calico 用 iptables 实现 NetworkPolicy，Cilium 用 eBPF 实现，性能更好。

六、总结

Kubernetes 网络的核心就三层：

  1. Pod 网络（CNI）：解决 Pod 之间怎么通的问题，靠 veth + 网桥 + Overlay 隧道（VXLAN）或 Underlay 路由（BGP）
  2. Service（kube-proxy）：解决服务发现和负载均衡的问题，靠 iptables/IPVS/eBPF 做 DNAT
  3. NetworkPolicy：解决访问控制的问题，靠 CNI 插件实现 Pod 级防火墙

理解了这三层，再看任何 Kubernetes 网络问题，都能定位到是哪一层出了问题。排查的时候按顺序来：先看 Pod IP 通不通（CNI层），再看 Service 能不能转发（kube-proxy层），最后看有没有 NetworkPolicy 拦截。
