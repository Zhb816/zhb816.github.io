零信任架构与 SD-WAN 融合——从边界防护到持续验证

传统网络安全的核心假设是”内网可信，外网不可信”，靠防火墙在边界上做访问控制。但远程办公、云迁移、供应链攻击让这个假设彻底失效了。零信任（Zero Trust）的核心是”从不信任，始终验证”，每一个访问请求都要经过身份认证、设备检查和授权，不管你来自内网还是外网。

这篇文章从零信任的原理讲到和 SD-WAN 的融合，最后看看 SASE 架构是怎么把这两者统一起来的。

一、传统边界安全模型的问题

传统企业网络像一个城堡：

  • 防火墙是护城河，只允许特定端口和协议进出
  • 内网是城堡内部，进去之后基本畅通无阻
  • VPN 是吊桥，远程用户通过 VPN 进入内网

这个模型在移动办公和云计算时代有几个致命问题：

1.1 横向移动无法防护

一旦攻击者通过钓鱼邮件、漏洞利用等方式进入内网（哪怕只是一台普通员工的电脑），因为”内网可信”，他可以在内网里横向移动，扫描其他服务器，窃取数据。2020 年的 SolarWinds 攻击就是典型案例，攻击者从一个软件更新渠道进入，然后横向渗透到多个政府机构。

1.2 VPN 是粗粒度的

传统 VPN 一旦连上，用户就获得了整个内网的访问权限，无法做到”只允许访问某个应用的某个端口”。而且 VPN 客户端本身就是攻击面，2020 年多个主流 VPN 厂商爆出严重漏洞。

1.3 云应用不在边界内

企业应用迁移到公有云后，流量不再经过企业边界防火墙，传统的安全策略无法覆盖云应用。用户直接从互联网访问 SaaS 应用，绕过了所有边界防护。

1.4 远程办公成为常态

疫情之后，大量员工长期远程办公，VPN 并发数不够、体验差、管理困难。把所有远程流量都拉回企业总部再转发，延迟高、体验差。

二、零信任的核心原则

NIST SP 800-207《Zero Trust Architecture》定义了零信任的七个基本原则：

  1. 所有数据源和计算服务都视为资源——不管是内网服务器、云应用、SaaS，都是需要保护的资源
  2. 所有通信都必须安全，不管来源网络——内网流量也要加密和认证，不能因为在内网就信任
  3. 对每个企业资源的访问授权是按会话授予的——不是一次登录永久有效，每次访问都要重新评估
  4. 访问由动态策略决定，包括用户身份、设备状态、请求上下文、行为分析——多维度评估，不是只看用户名密码
  5. 企业监控和度量所有基础设施的完整性和安全状态——持续监控设备和网络，发现异常立即响应
  6. 所有资源的身份认证和授权都是动态的，在允许访问之前严格执行——MFA、设备证书、实时风险评估
  7. 企业尽可能多地收集关于当前网络基础设施和通信状态的信息，用于改进安全态势——数据驱动的安全运营

简化成一句话：每一个访问请求，都要验证”你是谁、你的设备是否安全、你要访问什么、这个访问是否合理”，然后才决定是否允许，而且这个验证是持续的，不是一次性的。

三、BeyondCorp——谷歌的零信任实践

谷歌是零信任的先驱，2014 年发布了 BeyondCorp 系列论文，核心思想是把访问控制从网络层移到应用层，完全消除内网和外网的区别。

3.1 核心组件

  1. 设备清单（Device Inventory）：每台企业设备都有唯一标识，记录设备状态（操作系统版本、是否加密、是否安装安全软件、是否越狱/root）
  2. 身份提供商（Identity Provider）：用户身份认证，支持 SSO 和 MFA
  3. 访问代理（Access Proxy）：所有应用流量都经过代理，代理在转发请求前调用认证授权系统检查
  4. 访问控制引擎（Access Control Engine）：根据用户身份、设备信任级别、应用敏感度，动态决定是否允许访问
  5. 流量加密：所有通信都用 TLS 加密，包括内网流量

3.2 信任分级

BeyondCorp 不是简单的”允许/拒绝”，而是对设备和用户做信任分级：

  • 设备信任级别：高信任（企业管理、合规、加密）→ 中信任（企业管理但有小问题）→ 低信任（未管理设备）
  • 应用敏感度：低敏感（内部公告）→ 中敏感（内部工具）→ 高敏感（财务、生产系统）

访问决策 = 用户角色 + 设备信任级别 + 应用敏感度。比如高敏感应用只允许高信任设备从特定网络访问，低敏感应用可以从任何设备访问但需要 MFA。

3.3 没有 VPN

BeyondCorp 架构里完全没有 VPN。员工不管在办公室还是在家里，访问应用的方式完全一样：都经过访问代理，都要认证授权。内网和外网没有区别，因为根本不存在”内网”这个概念。

四、SDP——软件定义边界

SDP（Software Defined Perimeter）是零信任在网络层的实现，由 Cloud Security Alliance（CSA）提出。核心思想是先认证后连接，用户在通过身份认证之前，甚至看不到应用服务器的存在（服务器是”黑暗”的）。

4.1 SDP 架构

  • IH（Initiating Host，发起主机）：安装在用户设备上的 SDP 客户端
  • SDP Controller（控制器）：认证用户和设备，下发策略，管理网关
  • GW（Accepting Gateway，接受网关）：部署在应用前面，默认丢弃所有流量，只接受控制器授权的连接

4.2 连接建立流程

  1. IH 向控制器认证：用户输入凭据（+MFA），IH 发送设备信息（设备证书、操作系统状态、安全软件状态）给控制器
  2. 控制器评估：验证用户身份、检查设备合规性、根据策略决定允许访问哪些应用
  3. 控制器下发策略：告诉 IH 可以访问哪些网关，告诉 GW 接受来自这个 IH 的连接（通常是一个临时的加密隧道）
  4. IH 和 GW 建立加密隧道：通常用 IPSec 或 TLS/DTLS
  5. 用户通过隧道访问应用：GW 只转发到授权的应用和端口

关键点：在第 1-3 步完成之前，GW 对 IH 来说是完全不可见的，端口扫描扫不到，SYN 包被丢弃。这就是所谓的”黑暗互联网”（Dark Web）概念——不是 Tor 那个暗网，而是服务器对未认证用户完全隐身。

4.3 SDP vs VPN

维度 传统 VPN SDP
访问粒度 网络级（连上就能访问整个网段） 应用级（只能访问授权的应用和端口）
连接方式 先连接后认证 先认证后连接
服务器可见性 可见（可以扫描） 不可见（未认证时完全隐身）
加密 隧道加密，但内网流量不加密 端到端加密
设备检查 通常不做或只做基本检查 持续设备状态评估
性能 所有流量走VPN集中器 可以分布式部署，就近接入

五、SD-WAN 与零信任的融合——SASE

SD-WAN 解决的是”怎么连”的问题（智能选路、链路聚合、QoS），零信任解决的是”能不能连”的问题（身份认证、授权、加密）。两者天然互补，融合之后就是 SASE（Secure Access Service Edge）。

Gartner 在 2019 年提出 SASE 概念，把网络服务和安全服务统一到一个云原生的平台上：

5.1 SASE 架构

SASE 节点（PoP）分布式部署在全球各地，用户就近接入。每个 PoP 同时提供 SD-WAN 功能和安全功能，流量在 PoP 处完成智能选路、安全检查、加密，然后转发到目标。

5.2 SD-WAN + ZTNA 的融合点

  1. 身份感知的选路：SD-WAN 传统上只看应用类型和链路质量，融合零信任后，可以根据用户身份和设备信任级别选择不同的路径。比如高信任用户的关键业务走 MPLS 专线，低信任设备的流量先走安全检查节点再转发。

  2. 按身份做微分段：SD-WAN 的分段（Segmentation）传统上是按 VLAN 或 VRF 做的，融合零信任后，可以按用户身份、设备类型、应用做更细粒度的分段。同一个 VLAN 里，不同用户能访问的资源完全不同。

  3. CPE 作为零信任客户端：分支的 SD-WAN CPE 可以同时作为 SDP 客户端，在建立隧道之前先向控制器认证设备身份（设备证书），认证通过后才建立加密隧道。这样即使 CPE 被物理窃取，没有有效的设备证书也无法接入企业网络。

  4. 持续验证：SD-WAN 隧道建立后传统上就一直保持，融合零信任后，隧道生命周期内持续评估设备状态和用户行为，如果发现异常（比如设备突然出现恶意进程、用户行为异常），可以动态断开隧道或降级访问权限。

5.3 实际部署场景

场景一：远程办公

  • 员工安装 SASE 客户端（同时是 ZTNA 客户端和 SD-WAN 客户端）
  • 客户端先做身份认证（SSO + MFA）和设备检查
  • 认证通过后，客户端和最近的 SASE PoP 建立加密隧道
  • 访问企业应用时，PoP 做零信任授权检查，然后通过 SD-WAN 智能选路转发到应用
  • 访问互联网时，PoP 做 SWG 安全检查（URL过滤、杀毒、DLP）

场景二：分支互联

  • 分支的 SD-WAN CPE 用设备证书向 SASE 控制器认证
  • 控制器根据分支身份和策略，授权 CPE 可以访问哪些数据中心和云资源
  • CPE 和 SASE PoP 建立 IPSec 隧道，PoP 之间用 SD-WAN 智能选路
  • 分支到数据中心的流量：PoP 做安全检查（FWaaS），然后通过专线/互联网转发
  • 分支到 SaaS 的流量：本地突破（Local Breakout），不回传数据中心，PoP 做 CASB 检查

六、落地零信任的挑战

零信任听起来很美，但落地并不容易：

6.1 身份是基础

零信任的核心是身份，没有统一的身份体系（SSO、MFA、目录服务），零信任就是空中楼阁。很多企业的应用还在用本地账号，没有统一认证，这是最大的障碍。

6.2 设备可见性

要做设备信任评估，首先得知道企业有哪些设备、每台设备的状态是什么。很多企业连完整的设备清单都没有，更不用说持续监控设备安全状态了。

6.3 遗留应用

很多老应用不支持现代认证协议（SAML、OIDC），无法集成到零信任架构里。需要用访问代理（Reverse Proxy）做协议转换，或者用 SDP 网关在网络层做访问控制。

6.4 性能和体验

零信任要求每次访问都经过认证授权和安全检查，如果设计不好，会增加延迟、影响用户体验。SASE 用分布式 PoP 和云原生架构来解决这个问题，但自建零信任系统很容易做成”又慢又难用”。

6.5 渐进式落地

不要试图一步到位把所有应用都改成零信任。建议的路径：

  1. 先建统一身份（SSO + MFA）
  2. 先从远程办公场景切入，用 ZTNA 替代 VPN
  3. 逐步把高敏感应用接入零信任
  4. 最后覆盖所有应用和分支网络

七、总结

零信任不是一个产品，而是一种架构理念。它的核心是把安全边界从”网络边界”移到”身份和设备”，每一个访问请求都要经过多维度的动态验证。

SD-WAN 和零信任是天然互补的：SD-WAN 提供智能、高效的网络连接，零信任提供安全、细粒度的访问控制。两者融合形成的 SASE 架构，正在成为企业网络和安全的下一代标准。

对于运维工程师来说，理解零信任和 SASE 很重要，因为未来的网络运维不再只是配路由器和防火墙，而是要管理身份、设备、策略、云服务，网络和安全的边界会越来越模糊。

安全 > 网络架构
