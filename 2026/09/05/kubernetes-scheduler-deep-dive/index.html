Kubernetes 调度器深度解析——从 Filter 到 Score 的全链路与调优

Kubernetes 调度器（kube-scheduler）是 K8s 的核心组件之一，负责决定每个 Pod 跑在哪个节点上。很多人用 K8s 很久，只知道 Pod 会被自动调度到节点上，但调度器到底怎么选的节点？为什么有的 Pod 一直 Pending？亲和性、污点、优先级这些东西到底怎么工作的？这篇文章把 kube-scheduler 的内部机制彻底讲清楚。

一、调度器是什么

kube-scheduler 是 K8s 控制面的组件之一，运行在 master 节点上。它的核心职责就一个：监听新创建的、还没有分配节点的 Pod，为它们选择一个最合适的节点运行。

调度器不负责启动 Pod——它只是在 Pod 的 spec.nodeName 字段上填上选中的节点名，然后 kubelet 发现有 Pod 被调度到自己节点上，才负责拉取镜像、启动容器。

调度器的设计原则：

  • 可插拔：调度逻辑由一系列插件组成，可以自定义启用哪些插件、插件的顺序
  • 可扩展：通过调度框架（Scheduling Framework）可以编写自定义插件，不需要改调度器源码
  • 高性能：支持大规模集群（数千节点），调度延迟在毫秒级
  • 公平性：多租户、多队列调度，避免某个用户的 Pod 占满所有资源

二、调度流程总览

kube-scheduler 的调度流程分三个大阶段：

简单来说就是两步：

  1. 调度周期（Scheduling Cycle）：从所有节点中选出最合适的一个
  2. 绑定周期（Binding Cycle）：把 Pod 绑定到选中的节点上

调度周期是串行的（同一时间只有一个 Pod 在做调度决策），绑定周期是并行的（多个 Pod 可以同时绑定）。这样设计是为了保证调度决策的一致性，同时提高绑定的吞吐量。

下面逐个阶段详解。

三、调度队列

在进入调度流程之前，Pod 先进入调度队列。调度队列不是简单的 FIFO，而是一个优先级队列。

3.1 队列结构

调度队列有三个子队列：

  • ActiveQ（活跃队列）：等待调度的 Pod，按优先级排序。调度器每次从这里取 Pod 调度
  • BackoffQ（退避队列）：调度失败的 Pod 会进入这里，等待一段时间后再重试。退避时间指数增长（1s → 2s → 4s …，上限 10s），避免频繁重试浪费资源
  • UnschedulableQ（不可调度队列）：确定无法调度的 Pod（比如所有节点都不满足条件），放在这里。当集群状态变化时（新节点加入、节点资源释放、其他 Pod 删除），这些 Pod 会被重新移回 ActiveQ 重试

3.2 优先级排序

ActiveQ 里的 Pod 按优先级排序：

  1. 先按 Pod 的 priorityClassName 对应的优先级数值排序，高优先级在前
  2. 优先级相同的，按 Pod 创建时间排序，先创建的在前

这样保证高优先级的 Pod 先被调度。如果集群资源紧张，高优先级 Pod 可以抢占低优先级 Pod 的资源（后面讲抢占）。

3.3 事件驱动

调度器不是轮询队列，而是事件驱动的：

  • 有新 Pod 创建 → 加入 ActiveQ，触发调度
  • 有节点状态变化 → 触发 UnschedulableQ 里的 Pod 重试
  • 有 Pod 删除 → 触发 UnschedulableQ 里的 Pod 重试
  • 有 PV/PVC 变化 → 触发相关 Pod 重试

这样设计比轮询高效，而且响应快。

四、PreFilter——前置过滤

PreFilter 是调度流程的第一步，做一些预处理工作，为后续的 Filter 阶段准备数据。

PreFilter 阶段的插件：

  • NodeResourcesFit：计算 Pod 请求的资源总量，为后续节点资源过滤做准备
  • NodePorts：检查 Pod 需要的 HostPort，为后续端口冲突检查做准备
  • PodTopologySpread：计算拓扑分布约束，为后续分布检查做准备
  • InterPodAffinity：计算 Pod 亲和性/反亲和性的匹配项，为后续亲和性检查做准备
  • VolumeBinding：检查 PVC 的状态，为后续存储绑定做准备

PreFilter 的作用是把一些可以提前计算的东西先算好，避免在每个节点上重复计算，提高性能。如果 PreFilter 阶段发现 Pod 肯定无法调度（比如请求的资源超过任何节点的最大容量），可以直接拒绝，不进入后续阶段。

五、Filter——过滤节点

Filter 是调度流程的核心阶段之一，从所有节点中过滤掉不满足 Pod 运行条件的节点。

Filter 阶段会对每个节点依次运行一系列过滤插件，只要有一个插件认为这个节点不满足条件，这个节点就被淘汰。所有插件都通过的节点才进入下一个阶段。

5.1 核心过滤插件

1. NodeUnschedulable（节点不可调度）

  • 检查节点的 spec.unschedulable 是否为 true
  • 如果节点被标记为不可调度（比如 cordon 操作），过滤掉
  • 但如果 Pod 有容忍（toleration）对应 node.kubernetes.io/unschedulable 污点，可以通过

2. NodeName（节点名指定）

  • 如果 Pod 的 spec.nodeName 指定了节点名，只有那个节点能通过
  • 其他节点全部过滤掉

3. NodeResourcesFit（节点资源匹配）

  • 检查节点的可分配资源（Allocatable）是否满足 Pod 的资源请求（Requests）
  • 包括 CPU、内存、临时存储、扩展资源（如 GPU、SR-IOV）
  • 计算方式：节点已分配资源 + Pod 请求资源 <= 节点可分配资源
  • 已分配资源 = 节点上所有 Pod 的 Requests 之和（不是实际使用量，是请求量）
  • 这是最常用的过滤插件，大多数 Pending 的 Pod 都是因为这个过滤掉的

4. NodeAffinity（节点亲和性）

  • 检查 Pod 的 spec.affinity.nodeAffinity 是否满足
  • requiredDuringSchedulingIgnoredDuringExecution（硬约束）：必须满足，不满足就过滤
  • preferredDuringSchedulingIgnoredDuringExecution（软约束）：不强制，在 Score 阶段加权
  • 匹配规则：节点的 label 是否匹配 key/operator/values
  • operator 支持：In、NotIn、Exists、DoesNotExist、Gt、Lt

5. TaintToleration（污点容忍）

  • 检查节点上的污点（Taint），Pod 是否有对应的容忍（Toleration）
  • 节点有污点，Pod 没有对应容忍 → 过滤掉
  • 污点的 effect：
    • NoSchedule：不允许调度（硬约束）
    • PreferNoSchedule：尽量不调度（软约束，Score 阶段处理）
    • NoExecute：不允许调度，且已经在节点上的 Pod 如果没有容忍会被驱逐
  • 容忍的匹配：key、value、effect 都要匹配（或 key 为空匹配所有，effect 为空匹配所有 effect）

6. PodAffinity（Pod 亲和性）

  • 检查 Pod 和已运行 Pod 的亲和性关系
  • requiredDuringSchedulingIgnoredDuringExecution（硬约束）：必须和某些 Pod 在同一个拓扑域
  • 拓扑域由 topologyKey 定义，比如 kubernetes.io/hostname（同一节点）、topology.kubernetes.io/zone（同一可用区）
  • 匹配规则：命名空间 + label selector 匹配已运行的 Pod
  • 比如：”这个 Pod 必须和 app=web 的 Pod 在同一个可用区”

7. PodAntiAffinity（Pod 反亲和性）

  • 和 PodAffinity 相反，要求 Pod 不能和某些 Pod 在同一个拓扑域
  • 比如：”这个 Pod 不能和 app=db 的 Pod 在同一个节点”（避免单点故障）
  • 硬约束不满足就过滤，软约束在 Score 阶段加权

8. NodePorts（节点端口）

  • 检查 Pod 需要的 HostPort 是否和节点上已占用的端口冲突
  • 如果 Pod 声明了 hostPort，节点上该端口已被其他 Pod 占用 → 过滤

9. VolumeBinding（存储卷绑定）

  • 检查 Pod 引用的 PVC 能否在节点上使用
  • 如果 PVC 已经绑定了 PV，检查 PV 的节点亲和性是否满足（比如云盘只能在特定可用区使用）
  • 如果 PVC 还没绑定（WaitForFirstConsumer 模式），检查 StorageClass 能否在该节点上创建 PV
  • 这就是为什么 StorageClass 推荐用 WaitForFirstConsumer——等 Pod 调度到节点后再创建 PV，避免 PV 创建在 Pod 无法访问的可用区

10. VolumeZone（存储卷可用区）

  • 检查 PV 的可用区标签是否和节点的可用区匹配
  • 比如 AWS EBS 卷在 us-east-1a，就只能挂载到 us-east-1a 的节点上

11. VolumeLimits（存储卷数量限制）

  • 检查节点上已挂载的卷数量是否达到上限
  • 不同存储类型有不同的卷数量限制（比如 AWS EBS 每个节点最多 25 个卷）

12. PodTopologySpread（Pod 拓扑分布约束）

  • 检查 Pod 的拓扑分布约束是否满足
  • 控制 Pod 在拓扑域（节点、可用区、机架）中的分布均匀性
  • maxSkew 参数控制分布不均匀的最大偏差
  • whenUnsatisfiable：DoNotSchedule（硬约束，不满足就过滤）或 ScheduleAnyway（软约束，Score 阶段加权）

5.2 Filter 阶段的性能优化

Filter 阶段要对每个节点跑所有插件，节点多了会慢。调度器做了很多优化：

  • 并行过滤：多个节点的过滤并行执行
  • 短路：一个插件失败就跳过后续插件
  • 预计算：PreFilter 阶段提前算好公共数据
  • 缓存：节点信息、Pod 信息都有缓存，不需要每次都查 API Server
  • 增量更新：节点或 Pod 变化时只更新受影响的部分

大规模集群（5000+ 节点）下，Filter 阶段仍然能在几十毫秒内完成。

六、PostFilter——后置过滤与抢占

Filter 阶段结束后，如果没有任何节点通过过滤（所有节点都不满足条件），就进入 PostFilter 阶段。

PostFilter 阶段的核心是抢占（Preemption）：如果 Pod 优先级高，且集群中有低优先级 Pod 占用了资源，调度器可以尝试驱逐（删除）低优先级的 Pod，腾出资源给高优先级 Pod。

6.1 抢占的条件

抢占不是随便发生的，需要满足：

  1. Pod 有优先级（priorityClassName 不为空，且优先级数值 > 0）
  2. Filter 阶段所有节点都不满足
  3. 存在至少一个节点，驱逐该节点上某些低优先级 Pod 后，能满足当前 Pod 的运行条件
  4. 当前 Pod 的优先级高于被驱逐 Pod 的优先级
  5. 被驱逐的 Pod 没有保护机制（如 PodDisruptionBudget 不允许驱逐）

6.2 抢占的过程

  1. 调度器遍历所有节点，模拟驱逐节点上优先级低于当前 Pod 的 Pod
  2. 对每个节点，计算需要驱逐哪些 Pod、驱逐后能否满足当前 Pod
  3. 选出”代价最小”的节点：
    • 优先驱逐最少数量的 Pod
    • 优先驱逐优先级最低的 Pod
    • 优先驱逐高优先级 Pod 数量最少的节点
  4. 选中节点后，调度器通过 API Server 删除被选中的低优先级 Pod
  5. Pod 被删除后，资源释放，当前 Pod 在下一个调度周期被调度到该节点
  6. 被驱逐的 Pod 会重新进入调度队列，等待其他节点资源释放

6.3 抢占的注意事项

  • 抢占只删除 Pod，不保证被驱逐的 Pod 能在其他节点运行——它们可能也 Pending
  • 抢占是”优雅驱逐”，给 Pod 留 terminationGracePeriodSeconds 的时间清理
  • PodDisruptionBudget（PDB）可以保护 Pod 不被抢占——如果驱逐会导致 PDB 不满足，就不驱逐
  • 优先级为 0 或负数的 Pod 不能抢占其他 Pod
  • 系统关键 Pod（如 kube-proxy、CNI 插件）有很高的优先级，不会被抢占

七、PreScore 和 Score——打分排序

Filter 阶段过滤后，如果有多个节点都满足条件，就需要打分选出最优的一个。

PreScore 阶段做打分前的预处理，和 PreFilter 类似，提前算好公共数据。

Score 阶段对每个通过 Filter 的节点运行一系列打分插件，每个插件给节点打一个 0-100 的分数（0 最差，100 最好）。最终分数是所有插件分数的加权和。

7.1 核心打分插件

1. NodeResourcesBalancedAllocation（节点资源均衡分配）

  • 倾向于选择资源使用更均衡的节点
  • 计算 CPU 和内存的使用率，两者越接近（均衡），分数越高
  • 避免节点 CPU 用了 90% 但内存只用了 10% 这种不均衡的情况
  • 权重默认 1

2. NodeResourcesFit（节点资源匹配）

  • 倾向于选择剩余资源更合适的节点
  • 有两种打分策略：
    • LeastAllocated（默认）：剩余资源越多的节点分数越高（负载均衡，把 Pod 分散到各个节点）
    • MostAllocated：剩余资源越少的节点分数越高（装箱，把 Pod 集中到少数节点，节省节点）
  • 可以通过调度器配置选择策略
  • 权重默认 1

3. NodeAffinity（节点亲和性）

  • 对 preferredDuringSchedulingIgnoredDuringExecution 的软约束打分
  • 满足的偏好越多，分数越高
  • 权重默认 1

4. TaintToleration（污点容忍）

  • 对 PreferNoSchedule 污点打分
  • 节点上没有 PreferNoSchedule 污点，或 Pod 有对应容忍，分数高
  • 权重默认 1

5. PodAffinity / PodAntiAffinity（Pod 亲和/反亲和）

  • 对 preferred 的软约束打分
  • 满足亲和性的节点分数高，满足反亲和性的节点分数高
  • 权重默认 1

6. PodTopologySpread（Pod 拓扑分布）

  • 对 whenUnsatisfiable=ScheduleAnyway 的软约束打分
  • 分布更均匀的拓扑域分数高
  • 权重默认 1

7. ImageLocality（镜像本地性）

  • 倾向于选择已经有 Pod 需要的镜像的节点
  • 节点上已有的镜像越大、数量越多，分数越高
  • 避免拉取大镜像的开销
  • 权重默认 1

8. VolumeBinding（存储卷绑定）

  • 倾向于选择已经有绑定 PV 的节点，或需要创建更少新 PV 的节点
  • 权重默认 1

7.2 打分的加权机制

每个插件有一个权重（weight），最终分数 = Σ(插件分数 × 插件权重) / Σ(权重)。

权重可以在调度器配置里调整。比如想让资源均衡更重要，可以把 NodeResourcesBalancedAllocation 的权重调大。

默认配置下，大多数插件权重都是 1，公平竞争。生产环境可以根据业务特点调整权重，比如：

  • 数据库集群：提高 PodAntiAffinity 权重，让 Pod 分散到不同节点
  • 批处理任务：提高 NodeResourcesFit(MostAllocated) 权重，集中装箱节省节点
  • 多可用区部署：提高 PodTopologySpread 权重，保证跨可用区均匀分布

7.3 打分后的节点选择

所有节点打分完成后，分数最高的节点被选中。如果有多个节点分数相同（并列第一），随机选一个（实际上是按节点名排序后选第一个，但效果是随机的）。

选中节点后，进入 Reserve 阶段。

八、Reserve——预留资源

Reserve 阶段把选中节点上的资源”预留”给当前 Pod，避免后续调度的 Pod 把这些资源抢走。

具体操作：

  1. 在调度器内部的缓存中，把当前 Pod 的资源请求加到选中节点的已分配资源中
  2. 把 Pod 标记为”已预留”状态，关联到选中的节点
  3. 后续调度其他 Pod 时，Filter 阶段的 NodeResourcesFit 会把这些预留资源算进去

Reserve 是在调度器内存中操作的，不涉及 API Server，所以很快。如果后续绑定失败，会调用 Unreserve 把预留的资源还回去。

Reserve 阶段的插件：

  • 主要是 VolumeBinding 插件，把 PVC 标记为”预绑定”到该节点的 PV
  • 其他插件一般不需要在 Reserve 阶段做什么

九、Permit——批准

Permit 阶段是调度周期的最后一步，决定是否批准这个 Pod 进入绑定阶段。

Permit 插件可以：

  • 批准（Approve）：允许 Pod 进入绑定阶段
  • 拒绝（Deny）：拒绝 Pod，回到调度队列重试
  • 等待（Wait）：让 Pod 等待一段时间，期间可以被其他事件唤醒

Permit 的典型用途是批调度（Coscheduling）：一组 Pod 要么全部调度成功，要么都不调度。比如机器学习训练任务，需要 N 个 Worker Pod 同时运行，少一个都不行。Permit 插件可以让先调度成功的 Pod 等待，直到所有 Pod 都调度成功后再统一批准进入绑定。如果有 Pod 调度失败，等待的 Pod 全部拒绝，避免资源浪费。

默认配置下没有启用 Permit 插件，所有 Pod 直接批准。

十、绑定周期

调度周期完成后，Pod 进入绑定周期。绑定周期是并行执行的，多个 Pod 可以同时绑定。

10.1 WaitOnPermit——等待批准

如果 Pod 在 Permit 阶段被设置为 Wait 状态，在这里等待批准。批准后继续后续步骤。

10.2 PreBind——前置绑定

PreBind 阶段做绑定前的准备工作：

  • VolumeBinding：把 PVC 真正绑定到 PV（如果是 WaitForFirstConsumer 模式，在这里创建 PV 并绑定）
  • 其他需要在绑定前完成的操作

PreBind 失败的话，会 Unreserve 资源，Pod 回到调度队列重试。

10.3 Bind——绑定

Bind 是绑定周期的核心：调度器调用 API Server，把 Pod 的 spec.nodeName 设置为选中的节点名。

这一步很简单，就是一个 API 调用。但它是原子的——API Server 会检查 Pod 是否还存在、是否已经被绑定到其他节点，避免竞态条件。

绑定成功后，kubelet 会发现有 Pod 被调度到自己节点上，开始拉取镜像、启动容器。

10.4 PostBind——后置绑定

PostBind 阶段做绑定后的清理工作：

  • 清理调度器内部的缓存状态
  • 记录调度指标和日志
  • 触发相关的事件

PostBind 失败不影响绑定结果，因为 Pod 已经绑定成功了。

十一、调度框架与自定义插件

K8s 1.19 引入了调度框架（Scheduling Framework），把调度流程拆成了上面讲的这些扩展点（PreFilter、Filter、PostFilter、PreScore、Score、Reserve、Permit、PreBind、Bind、PostBind）。

每个扩展点都是一个接口，用户可以编写自定义插件实现这些接口，然后在调度器配置里启用。自定义插件和内置插件完全平等，可以一起工作。

11.1 编写自定义插件的场景

  • 网络感知调度：根据网络带宽、延迟选择节点
  • 硬件感知调度：根据 NUMA 拓扑、PCIe 设备、GPU 拓扑选择节点
  • 批调度：一组 Pod 同时调度
  • 成本感知调度：根据云资源成本选择节点（优先用便宜的竞价实例）
  • 业务规则调度：根据业务特定的规则选择节点

11.2 多调度器

K8s 支持同时运行多个调度器，每个 Pod 可以通过 spec.schedulerName 指定用哪个调度器。比如：

  • 默认调度器：调度普通 Pod
  • 自定义调度器：调度机器学习任务（支持批调度、GPU 拓扑感知）
  • 第三方调度器：如 Volcano（批处理调度）、Yunikorn（大数据调度）

多调度器之间通过 Pod 的 schedulerName 区分，互不干扰。

十二、常见调度问题排查

12.1 Pod 一直 Pending

Pod Pending 说明调度失败。排查步骤：

  1. 看 Pod 事件：

    Events 里会有调度失败的原因，比如：

    • 0/3 nodes are available: 3 Insufficient cpu. —— CPU 不够
    • 0/3 nodes are available: 3 node(s) didn't match node selector. —— 节点选择器不匹配
    • 0/3 nodes are available: 3 node(s) had untolerated taint. —— 污点不容忍
    • 0/3 nodes are available: 3 node(s) didn't find available persistent volumes. —— 存储问题

  2. 检查节点资源：

    看每个节点的 Allocated resources，CPU/内存是否已经满了

  3. 检查节点状态：

    节点是否 Ready，是否被 cordon（SchedulingDisabled）

  4. 检查亲和性/污点：

    • Pod 的 nodeSelector、nodeAffinity 是否有匹配的节点
    • 节点上的污点，Pod 是否有对应容忍

  5. 检查存储：

    • PVC 是否 Bound
    • PV 的节点亲和性是否匹配
    • StorageClass 是否正常

12.2 Pod 调度到了不合适的节点

  • 用 nodeAffinity 硬约束限制 Pod 只能在特定节点
  • 用 nodeAffinity 软约束引导 Pod 优先在某些节点
  • 用污点把特殊节点标记出来，只有有容忍的 Pod 才能调度
  • 用 PodTopologySpread 控制分布均匀性
  • 调整调度器打分插件的权重

12.3 调度慢

  • 集群规模大（几千节点）时，调度延迟会增加
  • 检查调度器的日志和指标（scheduling_duration_seconds）
  • 减少不必要的过滤插件和打分插件
  • 用节点分片（Node Sharding），多个调度器各管一部分节点
  • 升级 K8s 版本，新版本调度器性能持续优化

12.4 抢占不生效

  • 检查 Pod 的优先级是否真的高于被抢占的 Pod
  • 检查被抢占的 Pod 是否有 PDB 保护
  • 检查被抢占的 Pod 是否有 terminationGracePeriodSeconds 太长
  • 检查系统关键 Pod 的优先级（system-cluster-critical、system-node-critical）不会被抢占
  • 抢占只在 Filter 阶段所有节点都不满足时才触发，如果有节点满足条件，不会抢占

十三、生产环境调度最佳实践

13.1 资源规划

  • 所有 Pod 都要设置 Requests 和 Limits：这是调度器做资源决策的基础。不设置 Requests 的 Pod 被认为不占资源，可能导致节点超卖
  • Requests 要合理：设太小会导致节点超卖、实际运行时 OOM；设太大会浪费资源、调度困难
  • 用 LimitRange 设置默认值：命名空间级别设置默认的 Requests/Limits，避免用户忘记设置
  • 用 ResourceQuota 限制总量：命名空间级别限制总资源，避免一个团队占满集群

13.2 高可用调度

  • 用 PodAntiAffinity 把同一应用的 Pod 分散到不同节点：避免节点故障导致应用不可用
  • 用 PodTopologySpread 跨可用区分布：多可用区集群里，保证 Pod 均匀分布在各个可用区
  • 用 PDB 保护应用：设置 minAvailable 或 maxUnavailable，保证滚动更新和抢占时至少有一定数量的 Pod 可用
  • 关键 Pod 设置高优先级：核心业务 Pod 用高优先级，避免被低优先级 Pod 挤占资源

13.3 节点管理

  • 用污点标记特殊节点：GPU 节点、高内存节点、测试节点，打上污点，只有对应容忍的 Pod 才能调度
  • 用节点标签做分组：按可用区、机型、用途打标签，配合 nodeAffinity 使用
  • 维护前 cordon 节点：节点维护前先 cordon（标记不可调度），然后 drain（驱逐 Pod），避免维护期间有新 Pod 调度上来
  • 监控节点资源使用率：CPU/内存使用率超过 80% 时考虑扩容

13.4 存储调度

  • StorageClass 用 WaitForFirstConsumer：避免 PV 创建在 Pod 无法访问的可用区
  • 重要数据用 ReclaimPolicy: Retain：防止误删 PVC 导致数据丢失
  • 本地存储用 Local PV + nodeAffinity：Local PV 绑定到特定节点，配合 nodeAffinity 保证 Pod 调度到有数据的节点

十四、总结

kube-scheduler 的调度流程可以概括为：

  1. 入队：Pod 进入优先级调度队列，高优先级先调度
  2. PreFilter：预处理，算好公共数据
  3. Filter：从所有节点中过滤掉不满足条件的（资源、亲和性、污点、存储等）
  4. PostFilter：如果没有节点满足，尝试抢占低优先级 Pod
  5. Score：对满足条件的节点打分，加权求和选出最优
  6. Reserve：在选中节点上预留资源
  7. Permit：批准进入绑定阶段（支持批调度等待）
  8. Bind：把 Pod 绑定到选中的节点

理解了这个流程，遇到任何调度问题都能一步步定位：是 Filter 阶段被过滤了？还是 Score 阶段选了别的节点？还是抢占没生效？每一步都有对应的插件和日志可以查。

调度器的强大之处在于它的可扩展性——通过调度框架可以编写自定义插件，满足各种特殊的调度需求。生产环境要做好资源规划、高可用调度、节点管理、存储调度这几件事，才能让集群稳定高效地运行。
