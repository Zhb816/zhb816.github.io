OpenStack 架构深度解析——从组件协作到虚拟机创建全流程

OpenStack 是目前最主流的开源云平台，很多企业的私有云、运营商的公有云都是基于 OpenStack 搭建的。但 OpenStack 组件多、架构复杂，很多人用了很久也搞不清各个组件之间的关系。这篇文章从核心组件讲起，再走一遍虚拟机创建的完整流程，把 OpenStack 的架构理清楚。

一、OpenStack 是什么

OpenStack 是一个开源的云计算管理平台，提供 IaaS（基础设施即服务）能力。它不是一个单一的软件，而是由多个独立的项目组成，每个项目负责云平台的一个方面（计算、网络、存储、身份认证等），通过 REST API 协作。

OpenStack 的设计原则：

  • 模块化：每个组件独立开发、独立部署，可以按需启用
  • REST API：所有组件都提供 REST API，组件之间通过 API 通信
  • 消息队列：组件内部的不同服务之间通过消息队列（RabbitMQ/Qpid）通信，实现异步解耦
  • 数据库：每个组件有自己的数据库（MySQL/PostgreSQL），存储状态信息
  • 无状态服务：API 服务是无状态的，可以水平扩展，状态存在数据库和消息队列里

二、核心组件详解

OpenStack 有几十个项目，但核心的就这几个：

组件 项目名 功能
Keystone 身份认证服务 统一认证、授权、服务目录
Glance 镜像服务 虚拟机镜像的存储、注册、分发
Nova 计算服务 虚拟机的生命周期管理
Neutron 网络服务 虚拟网络、子网、路由、安全组、浮动IP
Cinder 块存储服务 云硬盘（块存储卷）的创建、挂载、快照
Swift 对象存储服务 对象存储，存镜像、备份、静态文件
Horizon 仪表盘 Web 管理界面

下面逐个详解。

2.1 Keystone——身份认证服务

Keystone 是 OpenStack 的入口，所有其他组件都要通过 Keystone 做身份认证。它提供：

  • 身份认证（Authentication）：验证用户是谁（用户名密码、Token、LDAP、联邦认证）
  • 授权（Authorization）：验证用户能做什么（基于角色的访问控制 RBAC）
  • 服务目录（Service Catalog）：记录所有 OpenStack 服务的 API 端点地址，用户通过服务目录找到各个服务的地址
  • 项目/租户（Project/Tenant）：资源的隔离单位，用户可以属于多个项目，每个项目有独立的资源配额

Keystone 的核心概念：

  • User（用户）：使用 OpenStack 的人或服务
  • Project（项目）：资源的容器，云主机、网络、存储都属于某个项目
  • Role（角色）：权限的集合，用户在某个项目里扮演某个角色
  • Token（令牌）：用户认证通过后获得的凭证，后续访问其他服务时携带 Token，不需要每次都输密码
  • Endpoint（端点）：每个服务的 API 访问地址，分 admin、internal、public 三种

工作流程：

  1. 用户用用户名密码向 Keystone 请求 Token
  2. Keystone 验证通过后，返回一个 Token + 服务目录（包含所有服务的 Endpoint）
  3. 用户拿着 Token 去访问 Nova（创建虚拟机）
  4. Nova 收到请求后，拿着 Token 去 Keystone 验证：这个 Token 有效吗？这个用户有创建虚拟机的权限吗？
  5. Keystone 验证通过，Nova 才继续处理请求

2.2 Glance——镜像服务

Glance 负责虚拟机镜像的管理。镜像就是虚拟机的模板，包含了操作系统和预装软件，创建虚拟机时从镜像启动。

Glance 提供：

  • 镜像的注册（记录镜像的元数据：名称、格式、大小、操作系统）
  • 镜像的存储（实际的镜像文件存在后端存储里，可以是 Swift、Ceph、本地文件系统、NFS）
  • 镜像的分发（创建虚拟机时，Nova 从 Glance 下载镜像）

镜像格式：

  • raw：原始格式，不压缩，性能好，但占用空间大
  • qcow2：QEMU 写时复制格式，支持压缩、快照、加密，空间利用率高，OpenStack 最常用
  • iso：光盘镜像，用于安装操作系统
  • aki/ari/ami：Amazon 内核/ramdisk/镜像格式

Glance 的后端存储可以配置多种，生产环境常用 Ceph 或 Swift。

2.3 Nova——计算服务

Nova 是 OpenStack 的核心，负责虚拟机的全生命周期管理：创建、启动、停止、重启、挂起、恢复、迁移、销毁、调整规格、快照。

Nova 不是一个单一的服务，而是由多个服务组成：

  • nova-api：接收和处理用户的 REST API 请求，做基本的校验，然后通过消息队列通知 nova-compute
  • nova-scheduler：调度器，决定虚拟机创建在哪个计算节点上。基于过滤（Filter）和加权（Weight）算法，从所有可用的计算节点中选出最合适的
  • nova-compute：运行在每个计算节点上，负责实际创建和管理虚拟机。通过调用 Hypervisor（KVM/QEMU、VMware、Xen、Hyper-V）的 API 来操作虚拟机
  • nova-conductor：数据库代理，nova-compute 不直接访问数据库，而是通过 nova-conductor 访问，避免数据库连接过多和安全问题
  • nova-novncproxy：VNC 代理，让用户通过浏览器访问虚拟机的控制台

Nova 创建虚拟机的大致流程：

  1. nova-api 收到创建请求，验证参数，写入数据库（状态为 BUILD）
  2. nova-api 通过消息队列通知 nova-scheduler
  3. nova-scheduler 执行调度算法，选出目标计算节点
  4. nova-scheduler 通过消息队列通知目标节点的 nova-compute
  5. nova-compute 从 Glance 下载镜像（如果本地没有缓存）
  6. nova-compute 调用 Neutron API 为虚拟机分配网络和端口
  7. nova-compute 调用 Cinder API 挂载系统盘（如果用卷启动）
  8. nova-compute 调用 libvirt API 创建并启动虚拟机
  9. 虚拟机启动成功后，nova-compute 更新数据库状态为 ACTIVE

2.4 Neutron——网络服务

Neutron 负责 OpenStack 的虚拟网络，提供网络即服务（NaaS）能力。它是 OpenStack 里最复杂的组件之一。

Neutron 的核心概念：

  • Network（网络）：一个二层广播域，类似 VLAN。可以是 VLAN、VXLAN、GRE、flat 等类型
  • Subnet（子网）：关联在 Network 上的三层网段，包含 CIDR、网关、DNS、DHCP 地址池
  • Port（端口）：虚拟机网卡在虚拟网络上的连接点，有 MAC 地址和 IP 地址
  • Router（路由器）：连接不同子网，实现三层转发。路由器有网关接口（连接外部网络）和内部接口（连接子网）
  • Floating IP（浮动IP）：公网 IP，绑定到虚拟机的端口上，实现外网访问虚拟机。通过 NAT 实现
  • Security Group（安全组）：虚拟机级别的防火墙，控制进出虚拟机的流量（基于 IP、端口、协议）
  • Provider Network（运营商网络）：直接映射到物理网络的虚拟网络，虚拟机直接获取物理网络的 IP

Neutron 的架构也是分布式的：

  • neutron-server：API 服务，处理请求，操作数据库
  • neutron-openvswitch-agent：运行在计算节点和网络节点上，配置 Open vSwitch，实现虚拟网络的数据面
  • neutron-l3-agent：运行在网络节点上，实现虚拟路由器（网络命名空间 + iptables）
  • neutron-dhcp-agent：运行在网络节点上，为子网提供 DHCP 服务（dnsmasq）
  • neutron-metadata-agent：提供元数据服务，虚拟机可以通过 169.254.169.254 获取自己的元数据（类似 AWS 的 instance metadata）

Neutron 的数据面实现：

  • ML2（Modular Layer 2）插件：Neutron 的核心插件，统一管理二层网络，支持多种网络类型驱动（VLAN、VXLAN、GRE、flat）和多种机制驱动（Open vSwitch、Linux Bridge、SR-IOV）
  • Open vSwitch：最常用的虚拟交换机，Neutron 通过 OVS 实现虚拟网络的数据转发
  • 网络命名空间：每个虚拟路由器和 DHCP 服务都在独立的网络命名空间里，实现隔离

2.5 Cinder——块存储服务

Cinder 提供云硬盘（块存储卷）服务，类似 AWS 的 EBS。云硬盘可以挂载到虚拟机上，作为数据盘使用，独立于虚拟机的生命周期。

Cinder 的核心概念：

  • Volume（卷）：一块虚拟的块存储设备，可以挂载到虚拟机
  • Snapshot（快照）：卷的某个时间点的副本，可以用来恢复卷或创建新卷
  • Volume Type（卷类型）：卷的规格，定义了后端存储类型、QoS、额外特性（SSD、HDD、复制、加密）
  • Backup（备份）：卷的备份，存在对象存储（Swift）里，用于灾难恢复

Cinder 的架构：

  • cinder-api：API 服务
  • cinder-scheduler：调度器，决定卷创建在哪个后端存储节点上
  • cinder-volume：运行在存储节点上，通过驱动（Driver）和后端存储通信，实际创建和管理卷
  • cinder-backup：备份服务，把卷备份到对象存储

Cinder 支持大量的后端存储驱动：Ceph RBD、LVM、NFS、GlusterFS、华为存储、EMC、NetApp 等。生产环境最常用的是 Ceph RBD。

2.6 Swift——对象存储服务

Swift 提供对象存储服务，类似 AWS 的 S3。对象存储是扁平的，没有目录结构，通过容器（Container）和对象（Object）来组织数据。

Swift 的特点：

  • 高可用：数据多副本存储（默认3副本），分布在不同的节点和磁盘上，节点故障不影响数据可用性
  • 高可扩展：通过增加节点线性扩展容量和性能，没有单点
  • 最终一致性：数据写入后，副本同步需要时间，短时间内可能读到旧数据（最终一致）
  • REST API：通过 HTTP REST API 访问，支持 GET/PUT/DELETE

Swift 的架构：

  • Proxy Server：代理服务器，接收用户请求，路由到正确的存储节点
  • Account Server：账户服务器，管理账户信息
  • Container Server：容器服务器，管理容器信息
  • Object Server：对象服务器，实际存储对象数据
  • Consistency Engine：一致性引擎，包括 Auditor（审计数据完整性）、Replicator（复制副本）、Updater（更新索引）

Swift 用 Ring（环）来决定数据存在哪个节点上。Ring 是一个一致性哈希环，把对象名映射到物理设备上。新增或移除节点时，只有少量数据需要迁移。

2.7 Horizon——仪表盘

Horizon 是 OpenStack 的 Web 管理界面，基于 Django 开发。它把所有组件的 API 封装成可视化的操作界面，让用户不用记命令就能管理云资源。

Horizon 分两个视图：

  • 用户视图：普通用户管理自己的云主机、网络、存储
  • 管理员视图：管理员管理所有项目、用户、配额、 hypervisor、实例迁移

三、虚拟机创建全流程

理解了各个组件，现在走一遍创建虚拟机的完整流程，看看各个组件是怎么协作的。

假设用户要创建一台虚拟机：2核4G、CentOS 7 镜像、默认网络、100G数据盘。

详细步骤：

第1步：认证
用户通过 Horizon 或 CLI 输入用户名密码，向 Keystone 请求 Token。Keystone 验证通过后返回 Token 和服务目录。

第2步：提交创建请求
用户拿着 Token，向 Nova API 发送创建虚拟机的请求，参数包括：镜像ID、规格（flavor）、网络ID、数据盘大小、密钥对等。

第3步：Nova API 处理
nova-api 验证参数合法性（镜像是否存在、规格是否合法、网络是否存在、配额是否足够），然后在数据库里创建虚拟机记录（状态 BUILD），通过消息队列发送请求给 nova-scheduler。

第4步：调度
nova-scheduler 收到请求后，执行调度算法：

  1. 过滤（Filtering）：从所有计算节点中过滤掉不满足条件的节点（资源不足、架构不匹配、可用性域不对、亲和性规则等）
  2. 加权（Weighting）：对剩余的节点打分，选出得分最高的节点（通常是剩余资源最多的节点，实现负载均衡）
  3. 把调度结果通过消息队列发给目标节点的 nova-compute

第5步：Nova Compute 准备
目标节点的 nova-compute 收到请求后：

  1. 检查本地是否有需要的镜像缓存，没有就从 Glance 下载镜像到本地
  2. 调用 Neutron API 创建一个端口（Port），分配 IP 地址和 MAC 地址
  3. 调用 Cinder API 创建系统盘（如果是卷启动）和数据盘，然后把卷挂载到计算节点（通过 iSCSI 或 RBD 映射）
  4. 生成虚拟机的 XML 配置文件（libvirt domain XML），包含 CPU、内存、磁盘、网络、VNC 等配置

第6步：创建虚拟机
nova-compute 调用 libvirt API，根据 XML 配置创建并启动 KVM 虚拟机。libvirt 会：

  1. 创建网络命名空间和 veth pair（如果用 Linux Bridge）或配置 OVS 端口（如果用 OVS）
  2. 创建 cgroup，限制 CPU 和内存
  3. 启动 QEMU 进程，加载镜像，启动虚拟机
  4. 配置 VNC 监听端口

第7步：虚拟机启动
虚拟机内部启动操作系统，通过 DHCP 获取 IP 地址（Neutron 的 DHCP agent 提供），启动完成后向 metadata service 请求元数据。

第8步：状态更新
nova-compute 检测到虚拟机启动成功，更新数据库里的虚拟机状态为 ACTIVE，同时通过消息队列通知 nova-api。用户在 Horizon 上看到虚拟机状态变为”运行中”。

整个流程涉及 Keystone、Nova（api/scheduler/compute/conductor）、Glance、Neutron、Cinder、libvirt 多个组件的协作，通过消息队列异步解耦，通过数据库共享状态。

四、OpenStack 的网络模型

Neutron 的网络模型是 OpenStack 里最容易让人困惑的部分，这里单独讲一下。

4.1 租户网络 vs 运营商网络

  • 租户网络（Tenant Network）：用户自己创建的虚拟网络，互相隔离。常用 VXLAN 或 GRE 封装，虚拟机 IP 是私网地址，通过虚拟路由器 + 浮动IP 访问外网
  • 运营商网络（Provider Network）：管理员创建的、直接映射到物理网络的网络。虚拟机直接获取物理网络的 IP，不需要 NAT，性能好但隔离性差

4.2 典型网络拓扑

  • VM1 和 VM2 在不同的子网，通过虚拟路由器互通
  • 虚拟路由器有一个网关接口连接外部网络
  • VM1 要访问外网，需要绑定浮动IP，路由器做 DNAT/SNAT
  • 同一个网络内的虚拟机直接二层互通，不需要经过路由器

4.3 数据面实现（以 OVS + VXLAN 为例）

计算节点上的网络数据流：

  • br-int（集成网桥）：所有虚拟机的 tap 设备都接在这个网桥上，负责 VLAN 标签的转换（内部 VLAN ID → 隧道 VNI）
  • br-tun（隧道网桥）：负责 VXLAN 隧道的封装和解封装，把二层帧封装成 VXLAN 报文发送到对端
  • 流表（Flow Table）：OVS 通过流表控制转发，Neutron 的 OVS agent 负责下发流表

安全组的实现：通过 iptables（Linux Bridge 模式）或 OVS 流表（OVS 防火墙驱动）实现，在虚拟机的 tap 设备前后过滤流量。

五、OpenStack 部署架构

生产环境的 OpenStack 部署通常分几个节点角色：

  • 控制节点（Controller）：运行 Keystone、Glance API、Nova API/Scheduler/Conductor、Neutron Server、Cinder API/Scheduler、Horizon、MySQL、RabbitMQ。控制节点是无状态的，可以多节点部署做高可用
  • 计算节点（Compute）：运行 Nova Compute、Neutron OVS Agent、Ceilometer Agent。实际跑虚拟机的节点，数量根据需求扩展
  • 网络节点（Network）：运行 Neutron L3 Agent、DHCP Agent、Metadata Agent。负责虚拟路由器和 DHCP。可以和控制节点合并，也可以独立部署（大规模时独立）
  • 存储节点（Storage）：运行 Cinder Volume、Swift Storage、Ceph OSD。提供块存储和对象存储

高可用部署：

  • 控制节点至少 3 台，做 HA（Pacemaker + HAProxy，或 Kubernetes 部署）
  • MySQL 主主复制或 Galera 集群
  • RabbitMQ 集群
  • 虚拟机通过 Nova 的 evacuate 功能在计算节点故障时迁移到其他节点

六、OpenStack vs 公有云 vs Kubernetes

经常有人问 OpenStack 和公有云、Kubernetes 的关系，简单对比一下：

维度 OpenStack 公有云(AWS/Aliyun) Kubernetes
服务类型 IaaS IaaS+PaaS+SaaS 容器编排(PaaS)
资源粒度 虚拟机 虚拟机+各种云服务 容器
部署方式 自建私有云 租用 自建或托管
适用场景 对数据安全要求高、需要完全控制基础设施的企业 不想自己运维基础设施、需要弹性扩展 微服务、云原生应用
关系 可以在 OpenStack 上跑 Kubernetes 公有云提供托管 Kubernetes Kubernetes 可以跑在 OpenStack 虚拟机上

实际上三者不是竞争关系，而是互补的：很多企业在 OpenStack 私有云上跑 Kubernetes 集群，Kubernetes 管理容器，OpenStack 管理底层虚拟机和网络。混合云场景下，OpenStack 私有云 + 公有云 + Kubernetes 统一编排是常见架构。

七、总结

OpenStack 的核心就六件事：

  1. Keystone：管身份认证和服务目录，是所有服务的入口
  2. Glance：管镜像，虚拟机的模板
  3. Nova：管计算，虚拟机的生命周期
  4. Neutron：管网络，虚拟网络、路由、安全组
  5. Cinder：管块存储，云硬盘
  6. Swift：管对象存储，存镜像和备份

各个组件通过 REST API + 消息队列 + 数据库协作，无状态服务可以水平扩展，有状态的部分（数据库、消息队列、存储）需要单独做高可用。

理解了组件职责和虚拟机创建流程，再看 OpenStack 的任何问题，都能定位到是哪个组件出了问题，然后针对性排查。OpenStack 虽然组件多，但每个组件的职责很清晰，掌握了核心六组件，其他组件（Heat 编排、Ceilometer 计量、Trove 数据库、Sahara 大数据等）都是在核心之上的扩展。

云计算 > OpenStack
