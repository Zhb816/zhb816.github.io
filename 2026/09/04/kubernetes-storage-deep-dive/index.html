Kubernetes 存储深度解析——PV、PVC、StorageClass 与 CSI 全链路

Kubernetes 的存储体系是很多人学 K8s 时最头疼的部分。PV、PVC、StorageClass、CSI、Provisioner、VolumeMode、AccessMode……概念一大堆，关系错综复杂。这篇文章从底层原理讲起，把 K8s 存储的全链路理清楚，包括动态供给的完整流程、CSI 的工作机制、常见存储类型的对比，以及生产环境的最佳实践。

一、为什么 Kubernetes 需要复杂的存储体系

容器是临时的，容器销毁后里面的数据就没了。但很多应用（数据库、日志、文件服务）需要持久化存储，数据不能丢。Kubernetes 不能直接把宿主机目录挂给容器——那样会和特定节点绑定，容器漂移到其他节点就访问不到数据了，而且多租户环境下也不安全。

所以 K8s 设计了一套抽象层，把”存储的供给”和”存储的使用”解耦：

  • 存储管理员：负责提供存储资源（创建 PV、配置 StorageClass）
  • 应用开发者：只需要声明需要多大的存储、什么访问模式（创建 PVC），不需要关心存储从哪来、怎么实现
  • Kubernetes：自动把 PVC 和合适的 PV 绑定，把存储挂载到容器里

这套解耦设计让应用开发者不需要懂底层存储（Ceph、NFS、云盘），存储管理员也不需要关心哪个应用在用存储。

二、核心概念详解

2.1 Volume（卷）

Volume 是 K8s 里最基础的存储概念，就是 Pod 里容器可以访问的一个目录。Volume 的生命周期和 Pod 绑定，Pod 销毁了 Volume 也没了（但数据可能还在底层存储上）。

K8s 支持几十种 Volume 类型，常见的：

  • emptyDir：Pod 调度到节点时创建的空目录，Pod 销毁就没了，用于临时数据、缓存
  • hostPath：把宿主机的目录挂进容器，有安全风险，只用于特定场景（如需要访问 Docker 套接字）
  • nfs：挂载 NFS 共享目录
  • cephfs / rbd：挂载 Ceph 文件系统或块存储
  • configMap / secret：把配置或密钥以文件形式挂进容器
  • persistentVolumeClaim：引用一个 PVC，使用持久化存储

emptyDir 和 hostPath 是节点本地存储，不能跨节点。持久化存储需要用 PV/PVC。

2.2 PV（PersistentVolume，持久卷）

PV 是集群里的一块存储资源，由管理员创建（或由 StorageClass 动态创建）。PV 是集群级别的资源，不属于任何命名空间。

PV 的关键属性：

访问模式（AccessModes）：

  • ReadWriteOnce（RWO）：只能被一个节点以读写模式挂载。最常用，大多数云盘和块存储只支持这个
  • ReadOnlyMany（ROX）：可以被多个节点以只读模式挂载
  • ReadWriteMany（RWX）：可以被多个节点以读写模式挂载。需要文件存储（NFS、CephFS、GlusterFS），块存储不支持
  • ReadWriteOncePod（RWOP）：只能被一个 Pod 挂载，K8s 1.27+ 引入，比 RWO 更严格

注意：访问模式是 PV 的能力声明，不是强制限制。即使 PV 支持 RWX，实际能不能多节点读写取决于底层存储。

回收策略（ReclaimPolicy）：

  • Retain：PVC 删除后，PV 保留，数据也保留，需要管理员手动清理。生产环境推荐
  • Delete：PVC 删除后，PV 和底层存储一起删除。动态供给默认是 Delete，有数据丢失风险，重要数据要改成 Retain
  • Recycle：已废弃，不推荐

PV 的状态（Phase）：

  • Available：可用，还没被绑定
  • Bound：已绑定到某个 PVC
  • Released：PVC 已删除，但 PV 还没被回收（Retain 策略时）
  • Failed：回收失败

2.3 PVC（PersistentVolumeClaim，持久卷声明）

PVC 是用户对存储的需求声明，属于某个命名空间。用户不需要知道 PV 的细节，只需要说”我要 10G 存储、读写模式、这个存储类”，K8s 自动找合适的 PV 绑定。

PVC 和 PV 的绑定规则：

  1. 存储类匹配：PVC 的 storageClassName 必须和 PV 的一致（或都为空）
  2. 访问模式匹配：PVC 要求的访问模式，PV 必须支持
  3. 容量匹配：PV 的容量必须 >= PVC 请求的容量
  4. 一对一绑定：一个 PV 只能绑定一个 PVC，绑定后 PV 就被独占了
  5. 静态绑定优先：如果有现成的 Available PV 满足条件，优先绑定；没有才走动态供给

绑定是单向的：PVC 绑定到 PV 后，即使有更小的 PV 释放出来，也不会重新绑定。

2.4 StorageClass（存储类）

StorageClass 是存储的”模板”，定义了动态创建 PV 的参数。有了 StorageClass，管理员不需要预先创建一堆 PV，用户创建 PVC 时，K8s 自动根据 StorageClass 创建 PV。

关键参数：

  • provisioner：决定了用哪个存储插件来创建 PV。可以是 in-tree（K8s 内置的，如 kubernetes.io/aws-ebs）或 CSI（容器存储接口，如 cephfs.csi.ceph.com）
  • parameters：传给 provisioner 的参数，不同存储类型参数不同。比如 Ceph 的 pool、CephFS 的 fsName、AWS EBS 的 type
  • reclaimPolicy：动态创建的 PV 的回收策略，默认 Delete
  • allowVolumeExpansion：是否允许 PVC 扩容。设为 true 后，用户修改 PVC 的 storage 请求大小，K8s 自动扩容 PV 和文件系统
  • volumeBindingMode：
    • Immediate：PVC 创建后立即绑定和创建 PV（默认）
    • WaitForFirstConsumer：延迟绑定，等第一个使用这个 PVC 的 Pod 被调度后，再根据 Pod 所在节点创建 PV。这样可以避免 PV 创建在 Pod 无法访问的节点上（比如云盘有可用区限制）。生产环境推荐用这个

默认 StorageClass：集群里可以有多个 StorageClass，其中一个可以标记为默认（annotation storageclass.kubernetes.io/is-default-class: "true"）。用户创建 PVC 时不指定 storageClassName，就用默认的。

2.5 CSI（Container Storage Interface，容器存储接口）

CSI 是 K8s 存储体系里最重要的演进。在 CSI 之前，K8s 的存储插件（in-tree）是写在 K8s 源码里的，每加一种存储都要改 K8s 代码、发版，存储厂商很痛苦，K8s 社区也维护不过来。

CSI 把存储插件从 K8s 核心里剥离出来，定义了一套标准的 gRPC 接口。存储厂商只要实现 CSI 接口，就能在 K8s 里用，不需要改 K8s 源码，插件可以独立部署和升级。

CSI 的规范定义了三类 gRPC 服务：

1. Identity Service（身份服务）

  • GetPluginInfo：返回插件名称和版本
  • GetPluginCapabilities：返回插件支持的能力（是否支持动态供给、是否支持扩容等）
  • Probe：健康检查

2. Controller Service（控制器服务）

  • CreateVolume：创建存储卷（动态供给）
  • DeleteVolume：删除存储卷
  • ControllerPublishVolume：把卷发布（挂载）到节点上（比如云盘挂载到 EC2 实例）
  • ControllerUnpublishVolume：从节点上卸载卷
  • ValidateVolumeCapabilities：验证卷的能力（访问模式、卷类型）
  • ListVolumes：列出所有卷
  • GetCapacity：获取存储池容量
  • ControllerExpandVolume：扩容卷
  • CreateSnapshot / DeleteSnapshot：创建/删除快照

3. Node Service（节点服务）

  • NodeStageVolume：在节点上格式化并挂载卷到全局目录（staging 路径）
  • NodeUnstageVolume：卸载 staging 路径
  • NodePublishVolume：把卷从 staging 路径绑定挂载到 Pod 的目录
  • NodeUnpublishVolume：解绑 Pod 目录
  • NodeGetVolumeStats：获取卷的使用情况（容量、inode）
  • NodeExpandVolume：节点上扩容文件系统
  • NodeGetCapabilities：节点能力

CSI 插件的部署架构：

  • Controller 组件：以 Deployment 或 StatefulSet 运行，负责卷的创建、删除、挂载到节点、扩容、快照。通常包含多个 sidecar 容器：
    • external-provisioner：监听 PVC，调用 CSI CreateVolume 创建卷，创建 PV
    • external-attacher：监听 VolumeAttachment，调用 CSI ControllerPublishVolume 把卷挂载到节点
    • external-resizer：监听 PVC 容量变化，调用 CSI ControllerExpandVolume 扩容
    • external-snapshotter：监听 VolumeSnapshot，调用 CSI CreateSnapshot 创建快照
    • csi-controller：存储厂商实现的 CSI 控制器驱动，实际执行 gRPC 调用
  • Node 组件：以 DaemonSet 运行在每个节点上，负责卷在节点上的格式化、挂载到 Pod。包含：
    • node-driver-registrar：把 CSI 驱动注册到 kubelet
    • csi-node：存储厂商实现的 CSI 节点驱动

这些 sidecar 是 K8s 官方维护的通用组件，存储厂商只需要实现 CSI driver（controller 和 node 的 gRPC 接口），不需要自己写 K8s 集成逻辑。

三、动态供给全流程

理解了概念，现在走一遍动态供给的完整流程，看看从用户创建 PVC 到容器里能访问存储，中间发生了什么。

场景：用户创建了一个 10G 的 PVC，StorageClass 是 csi-ceph-sc，provisioner 是 Ceph CSI，然后创建一个 Pod 挂载这个 PVC。

第1步：用户创建 PVC

K8s API Server 接收 PVC，状态为 Pending。

第2步：PV 控制器检查绑定
PV 控制器（运行在 kube-controller-manager 里）发现新的 PVC，开始找匹配的 PV：

  • 如果有现成的 Available PV 满足条件（存储类、访问模式、容量），直接绑定，PVC 状态变 Bound
  • 如果没有，且 PVC 指定了 StorageClass，走动态供给流程

第3步：external-provisioner 触发动态供给
external-provisioner（CSI controller pod 里的 sidecar）监听 PVC，发现这个 PVC 需要动态供给：

  1. 调用 CSI driver 的 CreateVolume gRPC 接口，传入卷名、容量、参数（从 StorageClass 的 parameters 来）
  2. CSI driver 调用底层存储 API（比如 Ceph 的 rbd create），实际创建存储卷
  3. CreateVolume 返回卷的 ID 和上下文信息
  4. external-provisioner 根据返回信息创建一个 PV 对象，PV 的 spec 里包含卷 ID、存储类、容量、访问模式、CSI 驱动信息
  5. PV 控制器把 PV 和 PVC 绑定，PVC 状态变 Bound

如果 StorageClass 的 volumeBindingMode 是 WaitForFirstConsumer，这一步会暂停，等 Pod 调度后再继续。

第4步：Pod 调度
用户创建 Pod，引用这个 PVC。kube-scheduler 调度 Pod 到某个节点。调度时会考虑卷的拓扑约束（比如云盘只能在特定可用区使用），WaitForFirstConsumer 模式下，provisioner 会等调度结果再创建 PV，确保 PV 创建在 Pod 能访问的位置。

第5步：external-attacher 挂载卷到节点
Pod 调度到节点后，kubelet 发现 Pod 有 PVC，需要挂载卷。kubelet 创建一个 VolumeAttachment 对象，表示”把这个卷挂载到这个节点”。

external-attacher 监听 VolumeAttachment：

  1. 调用 CSI driver 的 ControllerPublishVolume gRPC 接口，传入卷 ID 和节点 ID
  2. CSI driver 调用底层存储 API（比如 Ceph 的 rbd map，或 AWS 的 attach-volume），把卷挂载到目标节点
  3. 卷在节点上出现为一个块设备（如 /dev/rbd0）

第6步：kubelet 调用 CSI Node 格式化和挂载
卷挂载到节点后，kubelet 通过 CSI socket 调用节点上的 CSI node driver：

  1. NodeStageVolume：格式化块设备（如果是块存储且第一次使用），挂载到节点上的 staging 目录（如 /var/lib/kubelet/plugins/kubernetes.io/csi/pv/pv-name/globalmount）
  2. NodePublishVolume：把 staging 目录绑定挂载（bind mount）到 Pod 的卷目录（如 /var/lib/kubelet/pods/pod-uid/volumes/kubernetes.io~csi/pv-name/mount）

如果是文件存储（NFS、CephFS），没有 ControllerPublishVolume 这一步，直接 NodeStageVolume 挂载网络文件系统。

第7步：容器启动，访问存储
kubelet 启动容器，把 Pod 的卷目录挂载到容器里的指定路径（volumeMounts.mountPath）。容器里的应用就能读写这个目录了，数据存在底层存储上，容器销毁后数据还在。

删除流程（反过来）：

  1. 用户删除 Pod → kubelet 调用 NodeUnpublishVolume 解绑 → NodeUnstageVolume 卸载 staging
  2. kubelet 删除 VolumeAttachment → external-attacher 调用 ControllerUnpublishVolume 从节点卸载卷
  3. 用户删除 PVC → 如果 ReclaimPolicy 是 Delete，external-provisioner 调用 DeleteVolume 删除底层存储卷和 PV；如果是 Retain，PV 保留为 Released 状态，数据还在

四、常见存储类型对比

K8s 支持的存储类型很多，选择时要考虑性能、可靠性、访问模式、成本、运维复杂度。

存储类型 代表 AccessMode 性能 适用场景 缺点
公有云块存储 AWS EBS、阿里云盘、Cinder RWO 高 数据库、有状态应用 单节点挂载，有可用区限制
Ceph RBD 自建 Ceph 块存储 RWO 中高 数据库、通用块存储 运维复杂
CephFS 自建 Ceph 文件存储 RWX 中 共享文件、日志、内容管理 小文件性能一般
NFS 自建或 NAS RWX 低中 共享文件、静态资源 单点故障、性能差
GlusterFS 分布式文件存储 RWX 中 共享文件 社区不活跃
对象存储 S3、MinIO、Swift 不通过PV 高(并发) 图片、视频、备份、静态资源 不能直接挂载为文件系统(需s3fs)
Local PV 节点本地磁盘 RWO 极高 对延迟敏感的数据库 节点故障数据丢失，不能漂移

生产环境选型建议：

  • 数据库（MySQL、PostgreSQL、MongoDB）：用块存储（云盘或 Ceph RBD），RWO，IOPS 高的型号。不要用 NFS，性能和一致性都不行
  • 共享文件（多个 Pod 同时读写）：用 CephFS 或云厂商的 NAS（RWX）
  • 日志收集：可以用 HostPath 或 Local PV，日志不需要持久化到分布式存储
  • 大文件/静态资源：用对象存储，通过 SDK 访问，不要挂载为文件系统
  • 对延迟极度敏感：用 Local PV，但要做好应用层的数据冗余和故障转移

五、生产环境最佳实践

5.1 存储类配置

  • volumeBindingMode 用 WaitForFirstConsumer：避免 PV 创建在 Pod 无法访问的可用区，尤其是云盘场景
  • reclaimPolicy 用 Retain：重要数据的 StorageClass 一定要设 Retain，防止误删 PVC 导致数据丢失
  • allowVolumeExpansion 设为 true：允许在线扩容，避免空间不够时要重建卷
  • 多个 StorageClass 区分性能等级：比如一个 SSD 高性能类、一个 HDD 大容量类，让用户按需选择
  • 默认 StorageClass 要谨慎：默认类应该是最通用、最便宜的，高性能类不要设为默认

5.2 PVC 使用

  • 不要在 PVC 里写死 storageClassName：除非明确需要特定存储类，否则用默认类，提高可移植性
  • 合理设置容量：PV 绑定后不能缩小（大多数存储不支持缩容），容量要留余量但不要浪费
  • 重要数据定期备份：用 VolumeSnapshot 做快照，或用 Velero 做集群级备份
  • 监控卷使用率：用 kubelet 的 volume_stats 或 Prometheus 监控，防止磁盘写满

5.3 性能优化

  • 块存储用 ext4 或 xfs：xfs 更适合大文件和高并发，ext4 更通用
  • 数据库用 IOPS 高的存储类型：云盘选 SSD 或更高等级，Ceph 用 SSD 做 OSD 日志
  • 避免小文件大量随机读写：CephFS 和 NFS 对小文件随机读写性能差，尽量用块存储
  • Local PV 用于缓存：把缓存、临时数据放 Local PV，持久数据放分布式存储

5.4 安全

  • 不要用 hostPath：hostPath 可以访问宿主机文件系统，有容器逃逸风险，除非明确需要且做好安全上下文
  • 存储加密：敏感数据用存储层加密（云盘加密、Ceph 加密）或应用层加密
  • RBAC 限制 PVC 创建：多租户环境下，通过 ResourceQuota 限制每个命名空间的 PVC 数量和总容量，防止滥用

六、常见问题排查

PVC 一直 Pending：

  1. 没有匹配的 PV，且 StorageClass 的 provisioner 有问题 → 检查 provisioner pod 日志
  2. StorageClass 不存在或拼写错误 → kubectl get sc
  3. 容量不够，没有 PV 满足 → 检查 PV 容量
  4. WaitForFirstConsumer 模式，还没有 Pod 使用这个 PVC → 创建 Pod 后自动绑定

Pod 一直 ContainerCreating，挂载卷失败：

  1. 卷还没挂载到节点 → 检查 VolumeAttachment 状态，看 attacher 日志
  2. 格式化失败（比如已有文件系统但参数不对）→ 看 CSI node 日志，dmesg 看内核错误
  3. 节点上的 CSI driver 没运行 → 检查 DaemonSet pod
  4. 存储端权限问题 → 检查存储的访问权限、密钥

扩容不生效：

  1. StorageClass 的 allowVolumeExpansion 不是 true → 修改 StorageClass
  2. 文件系统没扩容 → 某些存储需要重启 Pod 触发 NodeExpandVolume，或手动扩容
  3. CSI driver 不支持扩容 → 检查插件能力

数据丢失：

  1. ReclaimPolicy 是 Delete，误删 PVC → 重要数据一定要设 Retain
  2. 节点故障，Local PV 数据丢失 → Local PV 不保证数据安全，重要数据不要用
  3. 存储端故障 → 检查存储集群健康状态，从备份恢复

七、总结

K8s 存储体系的核心就三层抽象：

  1. PV：集群里的存储资源，管理员管
  2. PVC：用户的存储需求声明，开发者管
  3. StorageClass：动态创建 PV 的模板，定义了用什么存储、什么参数

CSI 把存储插件从 K8s 核心剥离，存储厂商实现标准 gRPC 接口就能接入，是 K8s 存储的现在和未来。

动态供给的全流程：PVC 创建 → provisioner 调 CreateVolume 创建卷和 PV → 绑定 → Pod 调度 → attacher 调 ControllerPublish 挂载到节点 → kubelet 调 NodeStage 格式化挂载 → NodePublish 绑定到 Pod 目录 → 容器访问。

理解了这个流程，遇到任何存储问题都能一步步定位：是 PV 没创建？还是没绑定？还是没挂载到节点？还是节点上格式化失败？每一步都有对应的组件和日志可以查。
