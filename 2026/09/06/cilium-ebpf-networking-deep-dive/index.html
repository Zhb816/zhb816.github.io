Cilium 网络深度解析——eBPF 如何替代 kube-proxy 重定义 Kubernetes 网络

Cilium 是目前 Kubernetes 网络领域最火的 CNI 插件，基于 eBPF 技术，号称要替代 kube-proxy、iptables，提供更高性能、更强大的网络策略和可观测性。Google Kubernetes Engine（GKE）已经把 Cilium 作为默认数据面，AWS EKS、Azure AKS 也都支持 Cilium。这篇文章从底层原理讲起，看看 Cilium 到底怎么用 eBPF 重定义 K8s 网络。

一、传统 K8s 网络的问题

在讲 Cilium 之前，先看看传统 K8s 网络（kube-proxy + iptables/IPVS 模式）有什么问题。

1.1 kube-proxy 的工作原理

kube-proxy 运行在每个节点上，负责实现 Service 的负载均衡。它的核心工作是：

  • 监听 API Server，获取 Service 和 Endpoint 的变化
  • 在节点上生成 iptables 规则（或 IPVS 规则）
  • 当 Pod 访问 Service IP 时，iptables 做 DNAT，把目标地址改成某个后端 Pod 的 IP

1.2 传统方案的痛点

1. iptables 性能问题

  • iptables 规则是线性匹配的，Service 数量多了之后，每条包都要遍历很长的规则链，延迟增加
  • 大规模集群（几千个 Service）下，iptables 规则更新慢，CPU 占用高
  • iptables 不支持增量更新，每次 Service 变化都要重新加载整个规则集

2. IPVS 模式的局限

  • IPVS 比 iptables 性能好（用哈希表，O(1) 查找），但仍然需要 iptables 做包过滤和 SNAT
  • IPVS 只负责负载均衡，NetworkPolicy 还是要用 iptables 或其他方案
  • IPVS 的连接跟踪（conntrack）在高并发下有性能瓶颈

3. 可观测性差

  • iptables/IPVS 是黑盒，很难看到每个连接的详细信息
  • 排查网络问题只能靠 tcpdump、iptables -L，效率低
  • 没有内置的流量监控、策略命中统计

4. 功能有限

  • NetworkPolicy 只能基于 IP/端口，不能基于应用层（HTTP、gRPC、Kafka）
  • 不支持七层负载均衡
  • 不支持透明加密（需要额外的服务网格）
  • 多集群网络支持弱

Cilium 就是为了解决这些问题而生的——用 eBPF 在内核里做高效的包处理、负载均衡、网络策略，同时提供强大的可观测性。

二、Cilium 是什么

Cilium 是一个基于 eBPF 的 Kubernetes CNI 插件，提供：

  • Pod 网络：Pod 之间的网络连通性（CNI 标准接口）
  • Service 负载均衡：替代 kube-proxy，用 eBPF 做高性能负载均衡
  • NetworkPolicy：用 eBPF 做网络策略，比 iptables 更灵活、性能更好
  • 可观测性：内置 Hubble，提供网络流量的全栈可观测性
  • 高级功能：七层网络策略、透明加密、多集群、服务网格（Cilium Service Mesh）、带宽管理

Cilium 的核心设计理念：把网络数据面从 iptables/IPVS 搬到 eBPF，在内核里做高效的包处理，同时提供更丰富的功能和可观测性。

三、Cilium 的架构

Cilium 的核心组件：

3.1 Cilium Agent（DaemonSet）

运行在每个节点上，是 Cilium 的核心：

  • 监听 Kubernetes API，获取 Pod、Service、Endpoint、NetworkPolicy 的变化
  • 编译和加载 eBPF 程序到内核
  • 管理 eBPF Map（存储 Pod IP、身份、策略、负载均衡后端等信息）
  • 提供 CNI 接口（创建 Pod 时配置网络）
  • 提供 API 接口（供 Hubble、cilium CLI 使用）
  • 管理节点的网络配置（路由、ARP、邻居表）

3.2 Cilium Operator（Deployment）

集群级别的控制器，负责：

  • 管理 Cilium 的节点资源（CiliumNode CRD）
  • 分配 Pod CIDR（如果用 cluster-pool 模式）
  • 管理 Service 的负载均衡（在某些模式下）
  • 多集群相关的资源同步
  • 证书管理（如果启用了透明加密）

3.3 Hubble（可观测性）

Hubble 是 Cilium 内置的网络可观测性组件：

  • Hubble Relay：聚合所有节点的 Hubble 数据，提供集群级别的查询 API
  • Hubble UI：Web 界面，展示服务依赖图、流量拓扑、策略命中
  • hubble CLI：命令行工具，实时查看网络流量、DNS、HTTP、TCP 事件

Hubble 基于 eBPF 在内核里收集每个网络连接的信息（五元组、字节数、持续时间、协议、策略命中），不需要在 Pod 里注入 sidecar，零侵入。

3.4 eBPF 数据面

这是 Cilium 最核心的部分。Cilium 在每个节点上加载多个 eBPF 程序，挂载到不同的内核钩子上：

eBPF 程序 挂载点 功能
tc/ingress 容器网卡的入方向 Pod 入站流量处理：策略检查、负载均衡、连接跟踪
tc/egress 容器网卡的出方向 Pod 出站流量处理：策略检查、负载均衡、SNAT
XDP 物理网卡的最早接收点 节点入站流量的最早处理：DDoS 防护、快速路径
socket LB socket 创建/连接时 Service 负载均衡（在 socket 层就做 DNAT，性能最高）
cgroup cgroup 级别的钩子 主机命名空间的流量处理

四、Cilium 的核心技术

4.1 身份（Identity）模型

传统 K8s 网络策略基于 IP 地址——但 Pod IP 是动态变化的，Pod 重建后 IP 就变了，基于 IP 的策略管理起来很麻烦。

Cilium 引入了**身份（Identity）**模型：

  • 每个 Pod 根据它的 label 被分配一个数字身份（CiliumIdentity CRD）
  • 相同 label 的 Pod 共享同一个身份
  • 网络策略基于身份，而不是 IP
  • Pod 重建后，只要 label 不变，身份就不变，策略自动生效

身份的分配：

  • Cilium Agent 监听到 Pod 创建后，根据 Pod 的 label 计算身份
  • 如果已有相同 label 的身份，复用；否则创建新的身份
  • 身份信息存在 eBPF Map 里，key 是 Pod IP，value 是身份 ID
  • 网络策略也存在 eBPF Map 里，key 是身份 ID，value 是允许/拒绝的规则

这样做的好处：

  • 策略基于 label，语义更清晰（”允许 frontend 访问 backend”，而不是”允许 10.0.1.0/24 访问 10.0.2.0/24”）
  • Pod 重建不影响策略
  • 策略检查在 eBPF 里用身份 ID 做哈希查找，O(1) 性能，比 iptables 线性匹配快得多

4.2 Service 负载均衡（替代 kube-proxy）

Cilium 可以完全替代 kube-proxy，用 eBPF 实现 Service 负载均衡。有两种模式：

模式一：Socket LB（最高性能）
在 socket 层（应用调用 connect() 时）就做负载均衡和 DNAT：

  • eBPF 程序挂在 cgroup/socket 钩子上，拦截 connect() 系统调用
  • 查找 Service 的后端列表，选一个后端 Pod IP
  • 直接把 connect() 的目标地址改成后端 Pod IP
  • 包根本不需要经过协议栈的 NAT 处理，性能最高

这种模式下，从 Pod 到 Service 的连接，在 socket 层就被重定向到了后端 Pod，完全绕过了 iptables/IPVS。

模式二：TC/iptables 兼容模式
对于不支持 Socket LB 的场景（比如主机命名空间的进程、UDP 流量），Cilium 用 tc eBPF 程序做负载均衡，在 tc/ingress 或 tc/egress 钩子上做 DNAT。

负载均衡算法：

  • 随机（Random）：默认，随机选一个后端
  • 源地址哈希（Maglev）：一致性哈希，相同源 IP 总是到同一个后端，适合需要会话保持的场景
  • 轮询（Round Robin）：在 eBPF 里实现有状态的轮询

后端管理：

  • Service 的后端列表存在 eBPF Map 里（LPM trie 或哈希表）
  • Endpoint 变化时，Cilium Agent 增量更新 Map，不需要重新加载整个规则集
  • 支持会话亲和性、连接保持、优雅终止（terminating 状态的后端逐渐移除）

4.3 NetworkPolicy（网络策略）

Cilium 实现了 K8s 标准的 NetworkPolicy，还扩展了 CiliumNetworkPolicy（CNP）和 CiliumClusterwideNetworkPolicy（CCNP），支持更强大的策略：

标准 NetworkPolicy：

  • 基于 Pod label、namespace label、IP CIDR 的入站/出站规则
  • 基于端口的规则

CiliumNetworkPolicy 扩展：

  • 七层策略：基于 HTTP 方法/路径、gRPC 服务/方法、Kafka 主题、DNS 域名的策略
    • 例如：”只允许 frontend 调用 backend 的 /api/v1/* 路径，不允许 /admin”
    • 例如：”只允许查询 *.example.com 域名”
  • 基于身份的策略：基于 Cilium 身份，而不是 IP
  • 更细粒度的端口范围：支持端口范围、ICMP 类型
  • 策略审计模式：只记录不拒绝，用于策略上线前的验证
  • 策略命中统计：每个规则的命中次数、字节数

策略执行：

  • 策略规则存在 eBPF Map 里，key 是身份 ID + 端口 + 协议
  • tc/ingress 和 tc/egress 的 eBPF 程序查 Map 做策略检查
  • 命中拒绝规则的包直接丢弃，命中允许规则的包继续转发
  • 所有命中事件通过 perf ring 或 ring buffer 发送到用户态，供 Hubble 记录

4.4 连接跟踪（Conntrack）

Cilium 用 eBPF Map 实现了自己的连接跟踪表，替代内核的 conntrack：

  • 每个 TCP/UDP 连接的状态存在 eBPF Map 里
  • 支持 NAT 状态记录（做了 DNAT/SNAT 的连接）
  • 支持连接的字节数、包数统计
  • 比内核 conntrack 更高效，没有 conntrack 表满的问题
  • 可以针对每个连接做策略和监控

4.5 透明加密

Cilium 支持 Pod 之间的透明加密，有两种方式：

  • IPsec：基于内核 IPsec，在节点之间建立 IPsec 隧道，Pod 流量自动加密
  • WireGuard：基于 WireGuard 内核模块，性能更好，配置更简单

加密是节点到节点的，Pod 不需要做任何配置，流量离开节点时自动加密，到达对端节点时解密。适合对数据安全要求高的场景（比如金融、医疗、多租户）。

4.6 带宽管理（Bandwidth Manager）

Cilium 支持基于 eBPF 的带宽管理：

  • 为每个 Pod 设置带宽限制（egress 限速）
  • 用 eBPF + EDT（Earliest Departure Time）做高效的流量整形
  • 比传统的 tc qdisc（HTB、TBF）性能更好，延迟更低
  • 可以配合 Kubernetes 的 Traffic Control 或 Cilium 的注解使用

4.7 多集群（Cluster Mesh）

Cilium 支持多集群网络互联（Cluster Mesh）：

  • 多个 K8s 集群的 Pod 可以直接通信（Pod IP 路由）
  • 跨集群的 Service 发现和负载均衡（Global Service）
  • 跨集群的网络策略
  • 不需要 VPN 或特殊网关，节点之间直接路由（需要网络连通）
  • 支持基于身份的策略跨集群生效

适合多活数据中心、混合云、灾备等场景。

七、Cilium 部署和运维

7.1 部署模式

Cilium 有几种部署模式：

  • Overlay（隧道模式）：节点之间用 VXLAN 或 Geneve 隧道封装 Pod 流量，不需要底层网络支持 Pod IP 路由。最简单，适合大多数环境
  • Native Routing（直接路由模式）：Pod IP 直接在底层网络路由，不需要封装，性能最高。需要底层网络（交换机、路由器）支持 Pod CIDR 的路由，或者用 BGP 动态广播路由（配合 kube-router、MetalLB 等）
  • AWS ENI / Azure IPAM / GKE 模式：云厂商特定的 IPAM 模式，直接分配云厂商的辅助 IP 给 Pod，性能最高，没有封装

7.2 内核要求

Cilium 基于 eBPF，对内核版本有要求：

  • 最低：Linux 4.19（基本功能）
  • 推荐：Linux 5.10+（大部分功能）
  • 最佳：Linux 5.15+ / 6.x（所有功能，包括 Socket LB、带宽管理、WireGuard）

主流发行版支持：

  • Ubuntu 20.04+（5.4+ 内核）
  • CentOS 8 / RHEL 8（4.18 内核，但 backport 了 eBPF 特性）
  • CentOS Stream 9 / RHEL 9（5.14 内核）
  • 较新的云厂商托管 K8s（GKE、EKS、AKS）默认内核都满足

7.4 常见问题排查

Pod 之间不通：

  1. 检查 Cilium Agent 是否正常运行：kubectl get pods -n kube-system -l k8s-app=cilium
  2. 检查 Cilium 状态：cilium status
  3. 检查 eBPF 程序是否加载：cilium bpf metrics list
  4. 检查身份是否正确分配：cilium identity list
  5. 检查网络策略：cilium policy get
  6. 用 hubble observe 看流量在哪一跳被丢

Service 不通：

  1. 检查 Service 后端：cilium service list
  2. 检查 Socket LB 是否启用
  3. 检查 Endpoint 是否正常

性能问题：

  1. 检查是否用了 Overlay 模式（隧道封装有开销）
  2. 检查是否启用了 Socket LB（最高性能）
  3. 检查 eBPF 程序的验证器日志
  4. 用 cilium bpf metrics run 看 eBPF 程序的执行统计

八、Cilium Service Mesh

Cilium 最近在推服务网格（Cilium Service Mesh），目标是替代 Istio 这类 sidecar 模式的服务网格：

  • 不需要在每个 Pod 里注入 sidecar 代理
  • 用 eBPF 在内核里做七层流量管理（HTTP 路由、重试、超时、熔断）
  • 用 Envoy 做七层代理（按需部署，不是 sidecar，而是节点级或按需的代理）
  • 支持 mTLS、流量镜像、灰度发布、故障注入

Cilium Service Mesh 的优势：

  • 没有 sidecar 的资源开销（每个 Pod 少一个 Envoy 进程）
  • 延迟更低（内核层处理，不需要经过 sidecar 的用户态代理）
  • 运维更简单（不需要管理 sidecar 注入和升级）

目前 Cilium Service Mesh 还在快速发展中，七层功能相比 Istio 还不够完善，但 sidecarless 的方向是未来的趋势。

九、总结

Cilium 的核心就三点：

  1. eBPF 数据面：用 eBPF 程序替代 iptables/IPVS，在内核里做高性能的负载均衡、网络策略、连接跟踪
  2. 身份模型：基于 Pod label 的身份，而不是 IP，策略更清晰、性能更高
  3. 内置可观测性：Hubble 提供全栈网络可观测性，零侵入、低开销

Cilium 能做什么：

  • 替代 kube-proxy，Service 负载均衡性能更高
  • 实现 K8s NetworkPolicy，还扩展了七层策略（HTTP/gRPC/Kafka/DNS）
  • 提供网络可观测性（Hubble），排查网络问题更高效
  • 透明加密（IPsec/WireGuard）
  • 多集群互联（Cluster Mesh）
  • 带宽管理、服务网格

Cilium 不是没有门槛——它依赖较新的内核，eBPF 的概念比较多，学习曲线比传统方案陡。但它是 Kubernetes 网络的未来方向，GKE 已经默认采用，越来越多的企业在生产环境用 Cilium 替代传统的 kube-proxy + iptables 方案。作为运维和网络工程师，掌握 Cilium 和 eBPF 是必须的。
