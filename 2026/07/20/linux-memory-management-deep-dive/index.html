Linux 内存管理深度解析——伙伴系统、SLUB、页缓存与 OOM

Linux 内存管理是内核里最复杂的子系统之一，从物理页的分配回收，到虚拟地址的映射，再到页缓存和 OOM 杀手，每一层都有大量的算法和优化。理解内存管理，是排查内存泄漏、OOM、性能问题的基础。这篇文章从物理内存到虚拟内存，从分配到回收，逐层拆解。

一、物理内存组织

1.1 NUMA（Non-Uniform Memory Access）

现代多 CPU 服务器通常是 NUMA 架构：每个 CPU 有自己的本地内存，访问本地内存快，访问其他 CPU 的远程内存慢（要通过跨 CPU 互联总线）。

Linux 把每个 NUMA 节点的内存独立管理，分配内存时优先从当前 CPU 所在的 NUMA 节点分配（本地分配），本地内存不足时才从远程节点分配。

NUMA 相关的内存问题很常见：比如一个进程绑定在 CPU 0 上，但内存分配在了 node 1，导致每次内存访问都是远程访问，性能下降。可以用 numastat 查看进程的 NUMA 内存分布，用 numactl --cpunodebind=0 --membind=0 绑定 CPU 和内存节点。

1.2 Zones（内存区域）

每个 NUMA 节点的物理内存又被划分为多个 zone（区域），因为不同的物理地址范围有不同的用途和限制：

zone 地址范围（x86-64） 用途
ZONE_DMA 0-16MB 老式 ISA 设备的 DMA（24 位地址总线）
ZONE_DMA32 0-4GB 32 位设备的 DMA（只能访问 4GB 以下地址）
ZONE_NORMAL 4GB以上 正常内存，内核可以直接映射（线性映射）
ZONE_HIGHMEM （32位系统） 高端内存，内核不能直接映射，需要临时映射（x86-64 没有这个 zone）

x86-64 系统上主要用 ZONE_DMA32 和 ZONE_NORMAL，ZONE_DMA 基本不用了（没有 ISA 设备）。

每个 zone 有自己的空闲页链表（伙伴系统）、水位线（watermark）、统计信息。分配内存时根据请求的类型和限制选择合适的 zone，有一个 zone 列表的回退顺序（zonelist），比如优先从 ZONE_NORMAL 分配，不够再从 ZONE_DMA32 分配。

1.3 页（Page）

Linux 内存管理的基本单位是页（page），默认大小 4KB（x86-64）。也支持大页（HugePage）：2MB 和 1GB。

每个物理页对应一个 struct page 结构体，存在 mem_map 数组里（每个 NUMA 节点有自己的 node_mem_map）。struct page 记录了页的状态：引用计数、标志位、映射关系、所在的链表等。

struct page 非常紧凑（x86-64 上 64 字节），因为系统里有大量的页（32GB 内存有 800 万个页，800万 * 64字节 = 512MB，光 page 结构体就占 512MB）。

二、伙伴系统（Buddy System）——物理页分配器

伙伴系统是 Linux 物理内存的底层分配器，负责分配和回收连续的物理页。

2.1 原理

伙伴系统把物理内存按 2 的幂次分组成不同阶（order）的块：

  • order 0：1 页（4KB）
  • order 1：2 页（8KB）
  • order 2：4 页（16KB）
  • …
  • order 10：1024 页（4MB，最大 order，x86-64 上）

每个 order 有一个空闲块链表（free_area），共 11 个链表（order 0-10）。

分配：请求 order n 的块时：

  1. 先查 order n 的空闲链表，如果有，直接分配
  2. 如果没有，查 order n+1 的链表，找到一个块，分裂成两个 order n 的块（这两个块互为”伙伴”），一个分配出去，另一个加入 order n 的空闲链表
  3. 如果 order n+1 也没有，继续向上找，直到找到为止
  4. 分裂过程中产生的空闲伙伴块加入对应 order 的链表

回收：释放一个 order n 的块时：

  1. 检查它的伙伴块（地址相邻的另一个 order n 块）是否也空闲
  2. 如果伙伴也空闲，把两个块合并成一个 order n+1 的块
  3. 继续检查新块的伙伴是否空闲，合并，直到伙伴不空闲或达到最大 order
  4. 最终的块加入对应 order 的空闲链表

伙伴系统的优点：

  • 快速分配和回收（O(1)，链表操作）
  • 有效减少外部碎片（通过合并伙伴块）

伙伴系统的缺点：

  • 内部碎片：请求 5KB 内存，要分配 order 1（8KB），浪费 3KB
  • 不能分配小于 1 页的内存（小对象用 slab 分配器）
  • 长时间运行后仍然可能有碎片（虽然伙伴系统减少了碎片，但不能完全消除）

2.2 水位线（Watermark）

每个 zone 有三个水位线，用来控制内存分配和回收的行为：

  • min（最低水位）：空闲页低于这个值时，内存严重不足，分配会阻塞（等待回收）或失败
  • low（低水位）：空闲页低于这个值时，唤醒 kswapd 内核线程开始回收内存
  • high（高水位）：kswapd 回收内存直到空闲页达到这个值，然后停止回收

水位线的计算基于 zone 的大小和 vm.min_free_kbytes 内核参数（保留的最低空闲内存）。可以通过 /proc/sys/vm/min_free_kbytes 调整，增大这个值会让系统更早开始回收内存，减少直接回收的概率（直接回收会阻塞进程，影响性能），但也会浪费更多内存。

2.3 分配标志（GFP flags）

调用伙伴系统分配内存时，需要传入 GFP（Get Free Page）标志，告诉分配器这个分配的约束和行为：

  • GFP_KERNEL：内核分配，可以睡眠（阻塞等待回收），最常用
  • GFP_ATOMIC：原子分配，不能睡眠（中断上下文用），如果内存不够直接失败
  • GFP_USER：用户空间分配，可以睡眠
  • GFP_HIGHUSER：用户空间分配，优先从高端内存分配（32位系统）
  • GFP_DMA：从 ZONE_DMA 分配
  • GFP_DMA32：从 ZONE_DMA32 分配
  • GFP_NOIO：分配过程中不能触发 IO（比如在 IO 路径中分配，避免死锁）
  • GFP_NOFS：分配过程中不能触发文件系统操作（在文件系统代码中分配，避免死锁）
  • __GFP_ZERO：分配的页清零
  • __GFP_HIGHMEM：优先高端内存
  • __GFP_RETRY_MAYFAIL：重试，但可能失败
  • __GFP_NORETRY：不重试，失败直接返回

GFP 标志决定了分配时可以从哪些 zone 分配、是否可以睡眠、是否可以触发回收和 IO、失败后是否重试等。

三、SLUB 分配器——小对象分配

伙伴系统分配的最小单位是页（4KB），但内核里有大量小对象（比如 struct file、struct inode、task_struct、网络 sk_buff 等），大小从几十字节到几百字节，如果都用伙伴系统分配整页，内部碎片会非常严重。

SLUB（也叫 SLUB allocator，是 SLAB 的改进版，Linux 2.6.23 后默认）是内核的小对象分配器，在伙伴系统之上，把整页拆分成固定大小的对象，高效分配和回收小对象。

3.1 原理

SLUB 为每种对象类型创建一个 kmem_cache（缓存），每个缓存里的对象大小固定。比如：

  • kmalloc-64：64 字节对象的通用缓存
  • kmalloc-128：128 字节
  • kmalloc-256：256 字节
  • …
  • task_struct：进程描述符（约 2KB）
  • skbuff_head_cache：sk_buff 结构体
  • inode_cache：inode 结构体

每个 kmem_cache 由多个 slab 组成，每个 slab 是一个或多个连续的物理页（从伙伴系统分配），被拆分成多个固定大小的对象。

每个 slab 有三种状态：

  • full：所有对象都已分配
  • partial：部分对象分配，部分空闲（分配时优先从 partial slab 分配）
  • free：所有对象都空闲（长时间 free 的 slab 会被回收，页还给伙伴系统）

SLUB 用 per-CPU 的 partial slab 列表（cpu_slab）来加速分配，每个 CPU 有自己的 partial slab，分配时不需要加锁（无锁分配），只有 per-CPU 列表空了才需要从全局的 partial 列表获取，减少了锁竞争。

3.2 分配和回收

分配：

  1. 从当前 CPU 的 per-CPU partial slab 里找一个空闲对象，无锁分配
  2. 如果 per-CPU 列表空了，从全局的 partial 列表获取一个 slab 到 per-CPU
  3. 如果全局 partial 也空了，从伙伴系统分配新的页，创建一个新的 slab
  4. 从 slab 里取一个空闲对象返回

回收：

  1. 把对象标记为空闲，加入 slab 的空闲对象链表
  2. 如果 slab 从 full 变成 partial，加入 partial 列表
  3. 如果 slab 里所有对象都空闲了（变成 free slab），不会立即回收，而是保留在缓存里（避免频繁分配回收页）
  4. 内存紧张时（kswapd 回收），或缓存被收缩时，free slab 的页被回收，还给伙伴系统

3.3 kmalloc

kmalloc 是内核里最常用的内存分配函数，基于 SLUB 实现，分配一段连续的内核虚拟地址（也是连续的物理地址）。

kmalloc 有一系列大小等级（64、128、256、512、1024、2048、4096、8192…），分配时向上取整到最近的等级。比如 kmalloc(100, GFP_KERNEL) 会从 kmalloc-128 缓存分配，浪费 28 字节。

kmalloc 分配的内存在物理上是连续的（因为 SLUB 的 slab 是从伙伴系统分配的连续页），适合需要物理连续内存的场景（比如 DMA）。但分配大内存时（超过页大小的几倍），可能因为内存碎片而失败。

四、虚拟内存管理

4.1 虚拟地址和物理地址

Linux 用虚拟内存管理，每个进程有独立的虚拟地址空间，CPU 通过 MMU（Memory Management Unit）把虚拟地址翻译成物理地址。

x86-64 的虚拟地址空间布局（48 位有效地址，256TB）：

内核空间的虚拟地址和物理地址有一个固定的偏移（线性映射），__va(phys) = phys + PAGE_OFFSET，__pa(virt) = virt - PAGE_OFFSET。所以内核里大部分地址（kmalloc、全局变量）都是直接映射的，物理地址连续。

vmalloc 分配的虚拟地址是连续的，但物理地址不一定连续（通过页表映射到不连续的物理页），适合分配大内存（不需要物理连续），但有 TLB 刷新开销，不能用于 DMA。

4.2 页表（Page Table）

虚拟地址到物理地址的翻译通过页表实现。x86-64 用 4 级页表（5 级页表在 57 位地址系统上用）：

每个页表项（PTE）包含：

  • 物理页号（PFN）
  • 存在位（Present）：页是否在物理内存中
  • 读写位（R/W）：页是否可写
  • 用户/内核位（U/S）：用户态是否可访问
  • 访问位（Accessed）：页是否被访问过（用于回收算法）
  • 脏位（Dirty）：页是否被修改过（回收时需要写回磁盘）
  • NX 位（No Execute）：页是否不可执行（安全特性，防止代码注入）

大页（HugePage）可以减少页表级数：2MB 大页用 PMD 直接指向物理页（跳过 PTE），1GB 大页用 PUD 直接指向物理页。大页的好处是减少页表项数量、减少 TLB miss、提高翻译速度，但内存浪费更大（内部碎片）。

4.3 TLB（Translation Lookaside Buffer）

TLB 是 MMU 里的高速缓存，缓存最近使用的虚拟地址到物理地址的翻译结果。每次地址翻译先查 TLB，命中就直接用，不命中（TLB miss）才需要遍历页表（慢，因为页表在内存里，要多次内存访问）。

TLB 是 per-CPU 的，每个 CPU 有自己的 TLB。修改页表后（比如 munmap、fork 时写时复制），需要刷新 TLB（tlb_flush），让旧的翻译失效。TLB 刷新是有开销的（特别是多 CPU 系统，需要 IPI 中断其他 CPU 刷新），所以内核尽量减少 TLB 刷新。

大页可以显著减少 TLB miss（因为一个大页覆盖的地址空间大，需要的 TLB 项少），数据库等内存密集型应用常用大页提升性能。

五、页缓存（Page Cache）

页缓存是 Linux 性能的核心机制之一，把磁盘文件的内容缓存在内存里，减少磁盘 IO。

5.1 原理

当进程读取文件时，内核先检查页缓存里有没有对应的页：

  • 命中：直接从内存读取，不需要磁盘 IO
  • 未命中：从磁盘读取页到页缓存，然后从页缓存读取

写入文件时（默认 write 是回写模式）：

  • 数据先写入页缓存，标记为脏页（dirty）
  • 由内核线程 pdflush/flusher 周期性地把脏页写回磁盘
  • 进程不需要等待磁盘写入完成（异步写），除非用 fsync/O_SYNC 强制同步

页缓存用 address_space 结构管理，每个文件（inode）有一个 address_space，用基数树（radix tree，现在改成 XArray）索引文件偏移到页的映射。

页缓存里的页有两种类型：

  • 页缓存页（file-backed）：有文件 backing 的页，回收时如果干净直接丢弃，如果脏先写回磁盘再丢弃
  • 匿名页（anonymous）：没有文件 backing 的页（进程的堆、栈、mmap 的匿名内存），回收时换出到 swap 分区

5.2 LRU 链表

页缓存和匿名页都挂在 LRU（Least Recently Used）链表上，回收时按 LRU 算法回收最近最少使用的页。

LRU 链表分两种（每种又分 active 和 inactive）：

  • 文件页 LRU：页缓存页
    • active_file：活跃的文件页（最近被访问过，回收优先级低）
    • inactive_file：不活跃的文件页（最近没被访问，回收优先）
  • 匿名页 LRU：匿名页
    • active_anon：活跃的匿名页
    • inactive_anon：不活跃的匿名页

LRU 是双链表，新页加到头部，回收从尾部取（最久未使用）。页被访问时从当前位置移到头部（标记为活跃）。

内核参数 vm.swappiness（0-100，默认 60）控制回收时更倾向回收文件页还是匿名页：

  • 值高（接近 100）：更倾向回收匿名页（换出到 swap）
  • 值低（接近 0）：更倾向回收文件页（丢弃或写回），尽量不用 swap
  • 0：完全不换出匿名页（除非内存真的不够）

数据库等应用通常把 swappiness 设为 1-10，因为数据库的匿名页（缓存数据）比文件页更重要，不希望被换出。

5.3 写回机制

脏页（dirty page）由 flusher 内核线程（以前叫 pdflush）负责写回磁盘，触发条件：

  1. 周期性写回：每隔 vm.dirty_writeback_centisecs（默认 500，即 5 秒），flusher 线程醒来，把脏页写回
  2. 脏页比例超过阈值：
    • vm.dirty_background_ratio（默认 10%）：脏页占总内存比例超过这个值，唤醒 flusher 后台写回（不阻塞进程）
    • vm.dirty_ratio（默认 20%）：脏页比例超过这个值，进程的 write 会被阻塞，同步写回（防止脏页太多）
  3. 进程主动调用 fsync/fdatasync：强制把文件的脏页写回磁盘
  4. sync 系统调用：把所有脏页写回

六、内存回收

当内存不足时，内核需要回收一些页来满足新的分配请求。

6.1 kswapd（后台回收）

每个 NUMA 节点有一个 kswapd 内核线程，当空闲页低于 low 水位线时被唤醒，开始回收内存，直到空闲页达到 high 水位线。

kswapd 回收的页来源：

  1. 页缓存页：干净的页直接丢弃，脏页先写回磁盘再丢弃
  2. 匿名页：换出到 swap 分区（如果启用了 swap）
  3. slab 缓存：回收 free 状态的 slab（kmem_cache_shrink）

kswapd 是后台回收，不阻塞进程（异步）。但如果回收速度跟不上分配速度，空闲页继续下降到 min 水位线，就会触发直接回收。

6.2 直接回收（Direct Reclaim）

当进程分配内存时，如果空闲页低于 min 水位线，进程会自己参与内存回收（在分配路径中同步回收），这就是直接回收。

直接回收是阻塞的，进程要等回收完成才能继续分配，会导致进程延迟增加（卡顿）。生产环境里要尽量避免直接回收（通过增大 min_free_kbytes、调整 swappiness、增加内存等方式）。

直接回收时，如果回收的页是脏页，还要等 IO 写回完成，延迟更大。可以用 vm.dirty_ratio 和 vm.dirty_background_ratio 控制脏页比例，避免直接回收时遇到大量脏页。

6.3 内存压缩（Memory Compaction）

伙伴系统减少了外部碎片，但长时间运行后，仍然可能出现”总空闲内存够，但没有足够大的连续物理页”的情况（比如需要分配 order 5 的连续页，但空闲页都是零散的 order 0）。

内存压缩（compaction）通过移动已分配的页，把空闲页聚合成连续的大块。它把一个 zone 里的页从尾部往头部移动，把空闲页集中在尾部，形成连续的大块。

内存压缩由 kcompactd 内核线程在后台执行，也可以在分配大页失败时直接触发（直接压缩）。

如果高 order 的空闲块很少，说明碎片严重，可能需要触发压缩或重启。

七、OOM Killer（Out Of Memory）

如果内存回收（kswapd + 直接回收）后仍然不够，空闲页继续下降，内核会触发 OOM Killer，杀掉一个进程来释放内存。

7.1 OOM 选择算法

OOM Killer 选择杀哪个进程，基于 oom_score（每个进程有一个分数），分数最高的被杀掉。

oom_score 的计算考虑：

  • 进程占用的内存（RSS，包括页缓存和匿名页）——占主要因素
  • 进程的运行时间（运行久的进程分数低一些，尽量不杀）
  • 进程的 nice 值（nice 高的优先级低，分数高一些）
  • 是否是 root 进程（root 进程分数低一些）
  • 是否是内核线程（不杀）
  • oom_score_adj（用户可以调整，-1000 到 1000，-1000 表示永远不被杀）

OOM 的目标是：用最小的损失（杀最少的进程、杀最不重要的进程）释放足够的内存。

7.2 OOM 相关配置

  • vm.panic_on_oom：0（默认，OOM 时杀进程），1（OOM 时内核 panic，重启）。集群环境里有时设为 1，让故障节点快速重启，而不是半死不活。
  • vm.oom_kill_allocating_task：0（默认，杀分数最高的进程），1（杀触发 OOM 的当前进程）。
  • /proc/<pid>/oom_score_adj：调整进程的 OOM 分数，-1000 保护进程不被杀，1000 优先被杀。
  • /proc/<pid>/oom_score：只读，查看当前 OOM 分数。

容器环境里，OOM 是 cgroup 级别的（cgroup v2 的 memory.oom.group），当 cgroup 内存超过 memory.max 时，cgroup 里的进程会被 OOM kill。Docker 的 --memory 参数就是设置 cgroup 的内存限制，超过就 OOM kill 容器里的进程。

八、常见内存问题排查

8.1 内存泄漏

现象：进程的 RSS（常驻内存）持续增长，不释放，最终 OOM。

排查：

  1. top/htop 看哪个进程内存持续增长
  2. pmap -x <pid> 看进程的内存映射分布
  3. cat /proc/<pid>/smaps 详细看每个映射段的内存（RSS、PSS、Shared_Clean、Private_Dirty 等）
  4. 用 valgrind --leak-check=full 检测 C/C++ 程序的内存泄漏
  5. 用 gperftools/jemalloc 的内存分析功能
  6. Java 程序用 jmap -heap、jstat -gc、MAT 分析堆内存

注意：Linux 的内存管理是”尽量用内存”的，空闲内存会被用作页缓存，所以 free 命令里的 available 才是真正可用的内存（包括可以回收的页缓存），不要看到 free 低就以为内存不够。

8.2 OOM Kill

现象：进程突然被杀，dmesg 里有 OOM 日志。

排查：

  1. dmesg | grep -i oom 看 OOM 时的内存状态和被杀的进程
  2. 检查是系统级 OOM 还是 cgroup 级 OOM（容器）
  3. 系统级 OOM：看是否有进程内存泄漏，或内存确实不够
  4. cgroup 级 OOM：看容器的内存限制是否设置太小，或容器内进程内存泄漏
  5. 检查 vm.swappiness、vm.overcommit_memory、vm.overcommit_ratio 等参数

8.3 内存碎片

现象：总空闲内存够，但分配大的连续物理页失败（比如 dmesg 里有 order:5 的分配失败日志），或 slab 分配失败。

排查：

  1. cat /proc/buddyinfo 看各 order 的空闲块数量
  2. cat /proc/pagetypeinfo 更详细的页类型信息
  3. 手动触发压缩：echo 1 > /proc/sys/vm/compact_memory
  4. 长期运行的服务器建议定期重启，或用 kexec 快速重启
  5. 用大页（HugePage）避免碎片问题（大页预留后不会被碎片影响）

8.4 Swap 使用过多

现象：swap 使用率高，系统卡顿（swap in/out 频繁）。

排查：

  1. vmstat 1 看 si（swap in）和 so（swap out）列，非零说明在频繁换页
  2. 检查 vm.swappiness 是否设置过高
  3. 看哪些进程的匿名页被换出了：cat /proc/<pid>/smaps | grep Swap
  4. 数据库等应用建议关闭 swap（swapoff -a）或设 swappiness=1，避免数据库缓存被换出导致性能骤降
  5. 增加物理内存，从根本上减少 swap 使用

8.5 常用内存调优参数

参数 默认值 说明
vm.min_free_kbytes 自动计算 保留的最低空闲内存，增大可减少直接回收
vm.swappiness 60 回收倾向（0=优先文件页，100=优先匿名页）
vm.dirty_ratio 20 脏页比例上限，超过则阻塞写
vm.dirty_background_ratio 10 脏页比例触发后台写回
vm.dirty_writeback_centisecs 500 脏页写回周期（5秒）
vm.overcommit_memory 0 内存过量提交策略（0=启发式，1=总是允许，2=严格）
vm.overcommit_ratio 50 overcommit_memory=2 时的物理内存百分比
vm.panic_on_oom 0 OOM 时是否 panic
vm.compact_memory - 写 1 触发内存压缩
vm.drop_caches - 写 1 释放页缓存，2 释放 dentries/inodes，3 都释放

注意：drop_caches 只能释放干净的页缓存，脏页需要先 sync 写回才能释放。生产环境不要随便 drop_caches，会导致性能抖动（缓存失效，大量磁盘 IO）。

九、总结

Linux 内存管理的层次：

  1. 物理内存组织：NUMA 节点 → Zone（DMA/DMA32/NORMAL）→ 页（4KB/2MB/1GB）
  2. 物理页分配：伙伴系统（Buddy System），按 2 的幂次分配连续页，合并伙伴减少碎片
  3. 小对象分配：SLUB 分配器，在伙伴系统之上，把页拆分成固定大小对象，per-CPU 无锁分配
  4. 虚拟内存：4/5 级页表，MMU + TLB 地址翻译，vmalloc 非连续映射
  5. 页缓存：文件内容缓存，LRU 链表管理，脏页异步写回
  6. 内存回收：kswapd 后台回收 + 直接回收，LRU 算法，文件页 vs 匿名页（swappiness）
  7. OOM：内存不足时杀进程，基于 oom_score 选择
  8. cgroup 内存：per-cgroup 内存限制和统计，容器级 OOM

理解了这些层次，排查内存问题时就能从现象定位到具体层次：

  • 进程 RSS 持续增长 → 内存泄漏（应用层）
  • 系统 OOM → 回收不够或内存泄漏（回收层 + 应用层）
  • 大页分配失败 → 内存碎片（伙伴系统 + 压缩）
  • swap 频繁 → 内存不足或 swappiness 配置（回收层）
  • 写性能差 → 脏页比例过高或写回瓶颈（页缓存 + 写回）
  • 容器 OOM → cgroup 内存限制太小或容器内泄漏（cgroup 层）

内存管理是 Linux 内核最复杂的部分，这篇文章只是覆盖了核心概念和常见问题，深入学习还需要看源码（mm/ 目录）和相关论文。但掌握这些基础，足够应对日常运维中的大部分内存问题了。
