容器底层原理全拆解——namespace、cgroup、rootfs 与手动造容器

很多人用了很久 Docker/Kubernetes，但对容器的底层原理一知半解，以为容器是轻量级虚拟机。实际上容器根本不是虚拟机，它就是宿主机上的一个普通进程，只不过被 Linux 内核的几个特性”隔离”和”限制”了。这篇文章把容器的三大基石——namespace、cgroup、rootfs——从原理到实战全拆一遍，最后手动用 shell 命令造一个容器。

一、容器到底是什么

先破除一个误解：容器不是虚拟机。

维度 虚拟机 容器
隔离级别 硬件级（有独立的 Guest OS 内核） 进程级（共享宿主机内核）
启动速度 分钟级 毫秒级
资源开销 大（整个 Guest OS） 小（就是一个进程）
隔离强度 强（硬件隔离） 弱（内核特性隔离，有逃逸风险）
性能 有虚拟化开销 接近原生

容器的本质：宿主机上的一个进程，通过 namespace 实现视图隔离，通过 cgroup 实现资源限制，通过 rootfs 实现文件系统隔离。

Docker 做的事情，本质上就是：

  1. 调用 clone() 系统调用创建进程，同时传入各种 namespace 参数
  2. 把进程加入 cgroup，限制 CPU/内存/IO
  3. 用 overlayfs 构建容器的根文件系统，pivot_root 切换根目录
  4. 设置 capabilities、seccomp、AppArmor 等安全限制
  5. 启动进程

runc 是 OCI 运行时规范的参考实现，Docker 底层就是调用 runc 来创建容器的。runc 本质上就是一个封装了上述操作的二进制程序。

二、namespace——视图隔离

namespace 是 Linux 内核提供的一种机制，让进程看到的系统资源是隔离的。每个 namespace 里的进程，看到的资源和其他 namespace 里的进程不一样。

Linux 目前有 8 种 namespace：

namespace 隔离的资源 系统调用参数 内核版本
Mount 文件系统挂载点 CLONE_NEWNS 2.4.19
UTS 主机名和域名 CLONE_NEWUTS 2.6.19
IPC 信号量、消息队列、共享内存 CLONE_NEWIPC 2.6.19
PID 进程号 CLONE_NEWPID 2.6.24
Network 网络栈（网卡、IP、端口、路由表） CLONE_NEWNET 2.6.29
User 用户和组 ID CLONE_NEWUSER 3.8
Cgroup cgroup 根目录 CLONE_NEWCGROUP 4.6
Time 系统时间 CLONE_NEWTIME 5.6

下面逐个详解。

2.1 Mount namespace

Mount namespace 隔离文件系统的挂载点。每个 mount namespace 里的进程有自己独立的挂载表，在一个 namespace 里挂载/卸载文件系统不会影响其他 namespace。

容器启动时，会创建一个新的 mount namespace，然后把容器的 rootfs 挂载为根目录，这样容器里的进程看到的文件系统就是容器自己的，和宿主机完全隔离。

2.2 UTS namespace

UTS（UNIX Time-sharing System）namespace 隔离主机名和域名。每个 UTS namespace 里的进程可以有自己独立的主机名，修改主机名不影响其他 namespace。

容器里的 hostname 命令看到的就是容器自己的主机名（通常是容器 ID 的前 12 位）。

2.3 IPC namespace

IPC namespace 隔离 System V IPC（信号量、消息队列、共享内存）和 POSIX 消息队列。一个 IPC namespace 里的进程创建的 IPC 对象，其他 namespace 里的进程看不到。

2.4 PID namespace

PID namespace 隔离进程号。每个 PID namespace 里的进程有自己独立的 PID 空间，从 1 开始。PID 1 是该 namespace 里的 init 进程，负责回收僵尸进程。

PID namespace 是嵌套的，父 namespace 能看到子 namespace 里的所有进程（但 PID 不同），子 namespace 看不到父 namespace 里的进程。

注意：PID namespace 必须配合 --fork（unshare 先 fork 一个子进程，子进程进入新 namespace）和 --mount-proc（重新挂载 /proc，否则 ps 命令看到的还是宿主机的进程）。

2.5 Network namespace

Network namespace 隔离整个网络栈：网卡、IP 地址、端口、路由表、iptables 规则、/proc/net 目录等。每个 network namespace 有自己独立的网络栈，默认只有一个 lo 回环接口。

容器的网络隔离就是靠 network namespace 实现的。Docker 创建容器时：

  1. 创建一个新的 network namespace
  2. 创建一对 veth pair，一端放在容器 namespace（命名为 eth0），另一端放在宿主机（命名为 vethXXX），接到 docker0 网桥上
  3. 给容器的 eth0 分配 IP，设置默认路由

2.6 User namespace

User namespace 隔离用户和组 ID。一个在 user namespace 里的进程，可以在 namespace 里是 root（UID 0），但在宿主机上是一个普通用户（非特权 UID）。

这是容器安全的关键：容器里的 root 不是真正的宿主机 root，即使容器被攻破，攻击者拿到的也只是宿主机上的普通用户权限，攻击面大大减小。

User namespace 还允许非特权用户创建其他 namespace（mount、PID、network 等），这是 rootless 容器（podman rootless、nerdctl rootless）的基础。

User namespace 的 ID 映射通过 /proc/<pid>/uid_map 和 /proc/<pid>/gid_map 配置，格式是：namespace_id host_id length，比如 0 1000 1 表示 namespace 里的 UID 0 映射到宿主机的 UID 1000。

2.7 Cgroup namespace

Cgroup namespace 隔离 cgroup 根目录视图。在 cgroup namespace 里的进程，看到的 /proc/self/cgroup 是从该 namespace 的 cgroup 根开始的，而不是宿主机的 cgroup 根。这样容器里的进程看不到自己在宿主机 cgroup 层级中的位置，也看不到其他容器的 cgroup。

2.8 Time namespace

Time namespace 隔离系统时间。允许进程在 namespace 里看到不同的系统时间（通过偏移量实现），主要用于容器迁移（把容器从一台机器迁移到另一台机器时，保持时间一致）和测试（模拟时间流逝）。

三、cgroup——资源限制

namespace 解决的是”能看到什么”的问题（视图隔离），cgroup 解决的是”能用多少”的问题（资源限制）。

cgroup（Control Groups）是 Linux 内核提供的一种机制，用来把进程组织成层级的任务组，对每组进程进行资源限制、统计和控制。

3.1 cgroup v1 vs v2

cgroup 有两个版本：

cgroup v1：

  • 每种资源（CPU、内存、IO 等）有独立的层级（hierarchy），可以分别挂载
  • 控制器（controller）多，但配置复杂，不同控制器的层级可以不一致
  • 进程可以在不同控制器的不同 cgroup 里（一个进程的 CPU 在 cgroup A，内存在 cgroup B）
  • 历史悠久，兼容性好，但设计上有很多问题

cgroup v2（统一层级）：

  • 所有控制器共享同一个层级（unified hierarchy），挂载在 /sys/fs/cgroup
  • 一个进程在 cgroup 层级里只有一个位置，所有控制器对这个位置生效
  • 配置更简单，语义更清晰，支持更多新特性（如 cgroup namespace、PSI）
  • 内核 4.5 引入，5.2+ 稳定，现在主流发行版（Ubuntu 22.04、CentOS Stream 9、Fedora）默认用 v2

3.2 常用控制器

CPU 控制器：

  • cpu.max：限制 CPU 使用量，格式 $MAX $PERIOD，比如 50000 100000 表示在 100ms 周期内最多用 50ms，即 0.5 核
  • cpu.weight：CPU 权重（1-10000，默认 100），在 CPU 竞争时按权重分配
  • cpu.stat：CPU 使用统计（user、system、nr_periods、nr_throttled、throttled_time）

内存控制器：

  • memory.max：最大内存使用量（字节），超过会触发 OOM killer
  • memory.high：内存软限制，超过后内核会尽量回收内存，进程会被减速（ throttle），但不会 OOM
  • memory.low：内存保护，低于这个值的内存不会被回收（在内存压力时保护这个 cgroup）
  • memory.swap.max：swap 使用限制
  • memory.stat：内存统计（anon、file、kernel_stack、slab、sock、shmem 等）
  • memory.oom.group：OOM 时是否杀掉整个 cgroup 里的所有进程（而不是只杀一个）

IO 控制器：

  • io.max：限制 IO 速率，格式 $MAJ:$MIN rbps=$READ wbps=$WRITE riops=$READ_IOPS wiops=$WRITE_IOPS
  • io.weight：IO 权重（1-10000，默认 100）
  • io.stat：IO 统计

进程号控制器（pids）：

  • pids.max：最大进程/线程数，防止 fork 炸弹

3.4 PSI（Pressure Stall Information）

PSI 是 cgroup v2 引入的特性，用来度量资源压力（CPU、内存、IO），即”有多少时间因为资源不足而导致任务等待”。

PSI 可以用来做资源压力感知的自动扩缩容（比如 Kubernetes 的基于压力的调度），比单纯看 CPU 使用率更准确（CPU 使用率 100% 不一定有压力，可能是计算密集型任务；PSI 高才说明真的有任务在等资源）。

四、rootfs 和 overlayfs——文件系统隔离

namespace 隔离了挂载视图，但容器里的进程还需要一个独立的根文件系统（rootfs），否则它看到的还是宿主机的文件系统。

4.1 rootfs 是什么

rootfs 就是容器的根目录 / 里的所有文件，包括：

  • /bin、/sbin：可执行文件
  • /lib、/lib64：共享库
  • /etc：配置文件
  • /usr：用户程序
  • /var：可变数据
  • /dev、/proc、/sys：特殊文件系统（运行时挂载）

Docker 镜像本质上就是一个 rootfs 的打包（加上一些元数据）。Alpine 镜像的 rootfs 只有几 MB，Ubuntu 镜像的 rootfs 有几十 MB。

4.2 overlayfs——联合文件系统

容器的 rootfs 不是简单地把镜像解压到一个目录，而是用 overlayfs（联合挂载文件系统）把多个层（layer）联合挂载成一个根文件系统。

overlayfs 的核心概念：

  • lowerdir：只读层，镜像的层（可以有多个，从下到上叠加）
  • upperdir：可写层，容器运行时的修改都写在这里
  • workdir：工作目录，overlayfs 内部使用（必须和 upperdir 在同一个文件系统上）
  • merged：联合挂载后的视图，lowerdir + upperdir 的合并结果

关键机制：

  1. Copy-up（写时复制）：读取文件时，如果文件在 upperdir 里没有，就从 lowerdir 读；修改文件时，先把文件从 lowerdir 拷贝到 upperdir，然后在 upperdir 上修改。这样 lowerdir 永远不会被修改。
  2. Whiteout（隐藏）：删除文件时，在 upperdir 里创建一个特殊的字符设备文件（名为 .wh.<filename>），overlayfs 看到这个文件就知道对应的 lowerdir 文件被”删除”了，在 merged 视图里不显示。
  3. Opaque directory（不透明目录）：删除整个目录时，在 upperdir 里创建目录并设置 trusted.overlay.opaque 扩展属性，overlayfs 看到这个属性就知道这个目录是不透明的，lowerdir 里的同名目录内容被完全隐藏。

Docker 的镜像分层就是基于 overlayfs 的：每个 Dockerfile 指令（RUN、COPY、ADD 等）创建一个新的层（lowerdir），层是只读的，多个镜像可以共享相同的层（节省存储空间）。容器启动时，在镜像层之上加一个可写层（upperdir），容器的所有修改都在可写层里，删除容器时可写层也被删除，镜像层保持不变。

4.3 pivot_root——切换根目录

有了 rootfs 之后，还需要把容器进程的根目录从宿主机的 / 切换到容器的 rootfs。这通过 pivot_root 系统调用实现。

pivot_root 把当前进程的根文件系统切换到新的目录，同时把旧的根文件系统移动到一个子目录下（通常是 /.oldroot），之后可以卸载旧根。

chroot 也能改变进程的根目录视图，但 chroot 只是改变了 / 的解析，进程仍然可以通过其他方式访问宿主机文件系统（比如通过已经打开的文件描述符、通过 /proc/self/root 等）。pivot_root 是真正的根文件系统切换，更安全，容器用的是 pivot_root 而不是 chroot。

五、容器安全——capabilities、seccomp、AppArmor

除了 namespace 和 cgroup，容器还通过以下机制增强安全性：

5.1 Linux capabilities

传统的 Unix 权限模型是二元的：root（UID 0）拥有所有权限，普通用户没有任何特权。capabilities 把 root 的特权拆分成了几十个独立的能力，可以单独授予或撤销。

容器默认只授予一小部分 capabilities（而不是全部），即使容器里的进程以 root 运行，它的能力也远小于宿主机的 root。

常用的 capabilities：

  • CAP_NET_ADMIN：网络管理（配置网卡、路由、iptables）
  • CAP_NET_BIND_SERVICE：绑定 1024 以下的端口
  • CAP_SYS_ADMIN：系统管理（挂载、命名空间操作等，非常危险，默认不授予）
  • CAP_SYS_PTRACE：ptrace 其他进程
  • CAP_MKNOD：创建设备节点
  • CAP_SYS_MODULE：加载/卸载内核模块

Docker 默认授予的 capabilities：CAP_CHOWN, CAP_DAC_OVERRIDE, CAP_FOWNER, CAP_FSETID, CAP_KILL, CAP_SETGID, CAP_SETUID, CAP_SETPCAP, CAP_NET_BIND_SERVICE, CAP_NET_RAW, CAP_SYS_CHROOT, CAP_MKNOD, CAP_AUDIT_WRITE, CAP_SETFCAP。

5.2 seccomp

seccomp（secure computing mode）限制进程可以调用的系统调用。容器默认有一个 seccomp 配置文件，禁止调用一些危险的系统调用（比如 mount, ptrace, kexec_load, reboot 等），减少内核攻击面。

seccomp 用 BPF 过滤器实现，在内核的系统调用入口处检查，如果调用的系统调用在黑名单里，就返回错误（通常是 EPERM）或杀掉进程。

5.3 AppArmor / SELinux

AppArmor（Ubuntu/Debian 默认）和 SELinux（RHEL/CentOS 默认）是强制访问控制（MAC）系统，可以限制进程对文件、网络、能力的访问，即使进程以 root 运行也受限制。

Docker 默认给容器加载一个 AppArmor 配置文件（docker-default），限制容器的访问范围。

6.5 清理

七、容器的局限性和安全风险

理解了容器的原理，就能理解它的局限性：

  1. 共享内核：容器和宿主机共享同一个内核，内核漏洞会影响所有容器。容器逃逸（container escape）通常就是利用内核漏洞或 capabilities 配置不当实现的。
  2. 隔离不如虚拟机：namespace 隔离的是”视图”，不是真正的硬件隔离。某些资源（比如时间、内核参数、/sys 下的某些文件）没有完全隔离。
  3. cgroup 限制不完美：cgroup v1 有很多限制（比如不能限制 buffer cache、不能限制内核内存），cgroup v2 改进了很多，但仍然有一些资源不能精确限制（比如磁盘 inode 数、文件描述符数需要额外配置）。
  4. 镜像安全：容器镜像可能包含漏洞、恶意软件、敏感信息（密钥、证书）。需要用镜像扫描工具（Trivy、Clair）扫描，用最小基础镜像（distroless、scratch）减少攻击面。
  5. 运行时安全：容器运行时可能被攻击，需要用运行时安全工具（Falco、Sysdig）监控容器行为，检测异常系统调用和文件访问。

生产环境里的容器安全是一个体系：镜像扫描 + 最小 capabilities + seccomp + AppArmor/SELinux + 非 root 用户运行 + 只读根文件系统 + 运行时监控 + 网络策略（NetworkPolicy），多层防御。

八、总结

容器的三大基石：

  1. namespace：视图隔离，让进程看到独立的主机名、网络、进程、文件系统挂载、用户等。8 种 namespace 各司其职。
  2. cgroup：资源限制，限制进程组的 CPU、内存、IO、进程数等资源使用。v2 统一层级是未来方向。
  3. rootfs + overlayfs：文件系统隔离，用联合文件系统把镜像的只读层和容器的可写层联合挂载，pivot_root 切换根目录。

加上安全加固（capabilities、seccomp、AppArmor），就构成了完整的容器隔离体系。

理解了这些底层原理，再看 Docker、Kubernetes、containerd、runc 这些工具，就会发现它们本质上都是在管理 namespace、cgroup、rootfs 和镜像分层，只是封装程度和功能范围不同而已。遇到容器问题（网络不通、内存 OOM、文件丢失、权限不足），也能从底层原理出发快速定位。
