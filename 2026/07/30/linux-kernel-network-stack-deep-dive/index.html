Linux 内核网络栈深度解析——从网卡中断到 socket 接收队列

Linux 网络栈是内核里最复杂的子系统之一，从网卡收到一个包到应用程序读到数据，中间经过了几十个函数调用、多次内存拷贝、多个队列和调度点。理解这条路径，是做网络性能调优和排查网络问题的基础。这篇文章把接收和发送两条路径从里到外走一遍，再讲讲关键的性能优化技术。

一、核心数据结构

1.1 sk_buff（socket buffer）

sk_buff 是 Linux 网络栈的核心数据结构，一个 sk_buff 代表一个网络报文。它不是只存报文数据，而是包含了报文在协议栈各层的所有元信息。

关键点：

  • head/data/tail/end 四个指针：head 和 end 是缓冲区的边界，data 和 tail 是当前有效数据的边界。协议栈在头部添加数据时，data 指针往前移（push）；在尾部添加数据时，tail 指针往后移（put）。
  • frags 分页：大报文的数据可以分散在多个物理页里，不需要连续内存，提高内存利用率和拷贝效率（零拷贝的基础）。
  • frag_list 分片链表：GRO（接收合并）把多个小包合并成一个大包时，用 frag_list 链接，不需要实际拷贝数据。
  • 克隆（clone）：多个 skb 可以共享同一份数据（比如多播、连接跟踪），克隆时只复制 skb 结构体，不复制数据，用引用计数管理。

1.3 NAPI（New API）

NAPI 是 Linux 网络栈的中断处理机制，核心思想是中断 + 轮询：

  • 报文量少时：用中断，每个包触发一次中断，延迟低
  • 报文量多时：中断触发后，关闭中断，进入轮询模式，一次性处理多个包，减少中断开销

NAPI 结构里有一个 poll 函数指针和一个待处理报文的链表（gro_list 或 sk_buff_head），驱动在 poll 函数里从网卡的 RX ring 里取包。

2.1 网卡和 DMA

现代网卡都支持 DMA（Direct Memory Access），网卡收到报文后，不经过 CPU，直接通过 DMA 把报文数据写到内存里的 RX ring buffer。

RX ring 是一个环形缓冲区，由驱动初始化，每个元素是一个 sk_buff（或 page）的描述符，包含了数据的物理地址（DMA 地址）。网卡收到报文后，找到 ring 里的下一个空闲描述符，把数据 DMA 到对应的内存，然后更新描述符状态（标记为已使用），触发中断通知 CPU。

多队列网卡有多个 RX ring，每个 ring 对应一个中断号，可以绑定到不同的 CPU 核心，实现并行收包。网卡通过 RSS（Receive Side Scaling）把不同的流（基于四元组哈希）分配到不同的 ring，保证同一条流的包始终到同一个 ring（不乱序）。

2.2 硬中断和 NAPI 调度

网卡触发硬中断后，CPU 跳到中断向量表，执行驱动注册的中断处理函数。

中断处理函数做的事情非常少（硬中断上下文不能阻塞，要尽快返回）：

  1. 关闭网卡的接收中断（防止中断风暴）
  2. 调用 napi_schedule(&napi)，把 NAPI 结构加入到当前 CPU 的 softnet_data 的 poll_list 链表里
  3. 触发 NET_RX_SOFTIRQ 软中断

然后硬中断返回，CPU 回到被中断的上下文。

2.3 软中断和 NAPI poll

软中断（softirq）是 Linux 内核的一种延迟执行机制，NET_RX_SOFTIRQ 的处理函数是 net_rx_action()。

net_rx_action() 做的事情：

  1. 遍历当前 CPU 的 poll_list 链表（所有被调度的 NAPI 结构）
  2. 对每个 NAPI，调用它的 poll 函数（驱动实现）
  3. poll 函数从网卡的 RX ring 里取包，构建 sk_buff，交给协议栈
  4. poll 函数有预算限制（netdev_budget，默认 300 个包，或 2ms 时间限制），防止软中断占满 CPU
  5. 如果 poll 函数把 ring 里的包都取完了，重新开启网卡中断，把 NAPI 从 poll_list 移除
  6. 如果还有包没处理完（预算用完了），NAPI 留在 poll_list，下一次软中断继续处理

2.4 GRO（Generic Receive Offload）

napi_gro_receive() 会调用 GRO 逻辑，把多个属于同一条流的小包合并成一个大包，减少协议栈处理的报文数量。

GRO 的合并条件：

  • 同一条流（四元组相同）
  • 序号连续（TCP 序号连续）
  • 报文大小不超过 64K（或 MTU 的整数倍）
  • 标志位兼容（没有 FIN/RST 等）

合并后，多个小包变成一个大 skb（用 frag_list 链接，不实际拷贝数据），协议栈只需要处理一个大包，处理效率大幅提升。

GRO 是硬件 TSO/LRO 的软件替代，在不支持硬件 LRO 的网卡上也能获得类似效果。

2.5 netif_receive_skb——协议栈入口

netif_receive_skb() 是报文进入内核协议栈的入口函数。它做的事情：

  1. 设置 skb 的时间戳（如果开启了硬件时间戳）
  2. 遍历 ptype_all 链表：AF_PACKET 类型的 socket（tcpdump 就是用这个），所有报文都会先经过这里，这就是抓包的原理
  3. VLAN 处理：如果是 VLAN 报文，剥离 VLAN 头，找到对应的 VLAN 设备
  4. 桥接处理：如果接口加入了网桥（bridge），报文进入网桥处理逻辑（学习 MAC、转发/泛洪）
  5. 根据二层协议类型分发：
    • ETH_P_IP → ip_rcv()
    • ETH_P_IPV6 → ipv6_rcv()
    • ETH_P_ARP → arp_rcv()
    • 其他 → 对应的协议处理函数

2.6 三层处理（IPv4）

ip_rcv() 做的事情：

  1. 校验 IP 头（版本、长度、校验和）
  2. 检查报文长度是否合法
  3. 处理 IP 选项（严格源路由、时间戳等）
  4. 调用 NF_INET_PRE_ROUTING 钩子（Netfilter，iptables 的 raw/mangle 表在这里）
  5. 调用 ip_rcv_finish() → ip_route_input_noref() 做路由查找

路由查找的结果决定报文的走向：

  • 本地交付（目的 IP 是本机）→ ip_local_deliver()
  • 转发（目的 IP 不是本机，本机是路由器）→ ip_forward()
  • 组播/广播 → 特殊处理

ip_local_deliver()：

  1. 处理 IP 分片重组（如果报文是分片的，在这里等待所有分片到达后重组）
  2. 调用 NF_INET_LOCAL_IN 钩子（iptables 的 filter INPUT 表）
  3. 根据四层协议分发：
    • IPPROTO_TCP → tcp_v4_rcv()
    • IPPROTO_UDP → udp_rcv()
    • IPPROTO_ICMP → icmp_rcv()
    • 其他 → raw socket 或丢弃

2.7 四层处理（TCP）

tcp_v4_rcv() 做的事情：

  1. 校验 TCP 头和校验和
  2. 查找 socket：通过四元组（源IP、源端口、目的IP、目的端口）在 tcp_hashinfo 的哈希表里查找
    • 先查 established 哈希表（已建立连接的 socket）
    • 没找到再查 listening 哈希表（监听 socket，处理 SYN）
  3. 如果找到 socket，调用 tcp_v4_do_rcv() → 处理 TCP 状态机：
    • SYN 包：建立连接，分配新的 socket（child socket），放入 accept 队列
    • 数据包：放入 socket 的接收队列，更新 TCP 序号，发送 ACK
    • FIN 包：关闭连接
    • RST 包：重置连接
  4. 如果没找到 socket：发送 RST 复位（端口不可达）

2.8 Socket 接收队列和唤醒

TCP 数据最终被放入 socket 的 sk_receive_queue（接收队列）。然后：

  1. 如果 socket 是非阻塞的，设置 EPOLLIN 事件，通知 epoll
  2. 如果 socket 是阻塞的，唤醒在 wait_for_packet() 上睡眠的进程
  3. 进程被唤醒后，调用 read()/recv() 从接收队列里取数据，从内核空间拷贝到用户空间

三、发送路径（TX Path）

发送路径比接收路径简单一些：

3.1 应用层到传输层

应用调用 write()/send()，数据从用户空间拷贝到内核空间（copy_from_user），然后：

  • TCP：tcp_sendmsg() 把数据放入 socket 的发送缓冲区（sk_write_queue），受发送窗口和拥塞窗口控制，可能不会立即发送（Nagle 算法、延迟 ACK 等）
  • UDP：udp_sendmsg() 直接构建 UDP 报文，立即发送（无连接，不保证可靠）

TCP 的发送逻辑很复杂，涉及：

  • 滑动窗口（接收窗口 rwnd + 拥塞窗口 cwnd）
  • 拥塞控制（慢启动、拥塞避免、快速重传、快速恢复）
  • Nagle 算法（小包合并，减少小包数量）
  • 延迟 ACK（等一段时间或攒几个包再回 ACK）
  • TSO/GSO（大段卸载，把大包拆成 MTU 大小的包，由硬件或软件完成）

3.2 IP 层和邻居子系统

传输层构建好 skb 后，调用 ip_queue_xmit()（TCP）或 ip_send_skb()（UDP）：

  1. 构建 IP 头（源IP、目的IP、协议、TTL等）
  2. 路由查找（确定出接口和下一跳）
  3. 处理 IP 选项
  4. 调用 NF_INET_LOCAL_OUT 钩子（iptables OUTPUT 链）
  5. 调用 ip_output() → ip_finish_output() → ip_finish_output2()

ip_finish_output2() 进入邻居子系统（neighbour），查找下一跳的 MAC 地址：

  1. 查 ARP 缓存（neighbour table）
  2. 找到：获取 MAC，构建以太网头
  3. 没找到：发送 ARP 请求，缓存 skb，等 ARP 回应后再发送

3.3 qdisc（队列规则）

报文到达 dev_queue_xmit()，进入 qdisc（queueing discipline，队列规则）层。

qdisc 是 Linux 流量控制的核心，每个网卡的发送队列都有一个 qdisc，默认是 pfifo_fast（简单的先进先出，按 TOS 分三个优先级队列）。

qdisc 可以做：

  • 流量整形（Shaping）：限制发送速率（TBF、HTB）
  • 调度（Scheduling）：按优先级调度（pfifo_fast、PRIO、DRR）
  • 分类（Classification）：把报文分到不同的类（u32、fw、basic）
  • 主动队列管理（AQM）：队列满时主动丢包，避免全局同步（RED、CoDel、FQ_Codel）

默认的 pfifo_fast 很简单，按 TOS 把报文分到三个 band，高优先级 band 先发。生产环境里高带宽网卡推荐用 fq（Fair Queueing）或 mq（多队列）+ fq_codel。

qdisc 入队后，如果队列没满，报文被缓存，等待发送；如果队列满了，报文被丢弃（tail drop）。

3.4 驱动发送和 DMA

qdisc 出队后，调用驱动的 ndo_start_xmit() 函数（net_device_ops 里的函数指针）：

  1. 驱动把 skb 的信息（数据地址、长度）写入 TX ring 的下一个描述符
  2. 更新 TX ring 的 tail 指针
  3. 网卡通过 DMA 从内存读取数据，发送到网络
  4. 发送完成后，网卡触发发送完成中断，驱动释放 skb（dev_kfree_skb）

多队列网卡有多个 TX ring，内核通过 XPS（Transmit Packet Steering）把不同的流分配到不同的 TX queue，通常和接收的 CPU 对应（减少缓存失效）。

四、关键性能优化技术

4.1 RPS（Receive Packet Steering）

RPS 是软件版的 RSS，在不支持多队列的网卡上，把报文在软中断里分发到不同的 CPU 处理。

原理：NAPI poll 取到包后，计算报文的哈希值（四元组哈希），根据哈希把报文放到目标 CPU 的 backlog 队列里，触发目标 CPU 的 NET_RX_SOFTIRQ，由目标 CPU 继续处理协议栈。

RPS 可以把协议栈处理分散到多个 CPU，避免单个 CPU 成为瓶颈。但 RPS 有跨 CPU 的队列开销，不如硬件多队列（RSS）效率高。

4.2 RFS（Receive Flow Steering）

RFS 是 RPS 的增强版，RPS 只根据哈希选 CPU，RFS 会根据应用程序在哪个 CPU 上运行来选 CPU，让报文处理的 CPU 和应用运行的 CPU 尽量一致，提高 CPU 缓存命中率。

RFS 需要配合 rps_sock_flow_entries 和每个队列的 rps_flow_cnt 配置。

4.3 XPS（Transmit Packet Steering）

XPS 把发送队列和 CPU 绑定，某个 CPU 上的应用发送的报文，始终从同一个 TX queue 发出，减少锁竞争和缓存失效。

4.4 繁忙轮询（Busy Poll）

默认情况下，应用阻塞在 read() 上，等报文到达后被唤醒。繁忙轮询模式下，应用在 read() 里主动轮询网卡的接收队列，不睡眠，延迟更低（但消耗 CPU）。

开启方式：

  • socket 级别：setsockopt(fd, SOL_SOCKET, SO_BUSY_POLL, &usecs, sizeof(usecs))
  • 全局：echo 50 > /proc/sys/net/core/busy_poll（微秒）

适合低延迟场景（高频交易、实时游戏），但会消耗大量 CPU，不适合高吞吐场景。

4.5 GRO/GSO/TSO/LRO

这些都是大包合并/拆分技术，减少协议栈处理的报文数量：

  • GRO（Generic Receive Offload）：接收端软件合并小包，前面讲过
  • LRO（Large Receive Offload）：接收端硬件合并小包，网卡硬件完成，比 GRO 快，但可能违反 TCP 规范（合并时不检查序号），在路由器/网关上不能用
  • GSO（Generic Segmentation Offload）：发送端软件拆分大包，协议栈处理一个大包，到驱动前再拆成 MTU 大小的包
  • TSO（TCP Segmentation Offload）：发送端硬件拆分大包，网卡硬件完成 TCP 分段，比 GSO 快，减轻 CPU 负担

4.7 内核旁路（Kernel Bypass）

对于极致性能场景（10G/25G/100G 线速处理），内核网络栈的开销仍然太大（中断、软中断、内存拷贝、协议栈处理），需要内核旁路技术：

  • DPDK（Data Plane Development Kit）：用户态驱动，直接操作网卡寄存器，绕过整个内核网络栈，在用户态收包发包。性能极高（线速），但需要独占网卡和 CPU，不能和内核网络栈共存。
  • XDP（eXpress Data Path）：前面讲过，在网卡驱动层、协议栈之前用 eBPF 程序处理报文，不需要完全旁路内核，可以和内核网络栈共存（XDP_PASS 把包上送协议栈）。
  • Netmap：类似 DPDK 的用户态网络框架，用共享内存的方式在用户态和网卡之间传递报文。
  • RDMA（Remote Direct Memory Access）：远程直接内存访问，绕过 CPU 和内核，网卡直接读写对端内存，延迟极低（微秒级），用于高性能计算和存储网络。

五、常见网络问题排查思路

理解了网络栈路径，排查问题时就能按路径定位：

  1. 网卡层：ethtool -S eth0 看网卡计数器（rx_dropped、tx_dropped、errors），ethtool -i eth0 看驱动版本，dmesg 看网卡报错
  2. 中断层：cat /proc/interrupts 看中断分布是否均匀，top 看软中断 CPU 使用率（si 列）
  3. 协议栈层：netstat -s 看协议统计（TCP 重传、丢包、连接失败），ss -ti 看连接的详细状态（cwnd、rtt、重传）
  4. Socket 层：ss -lntp 看监听队列（Recv-Q、Send-Q），接收队列满说明应用处理不过来
  5. qdisc 层：tc -s qdisc show dev eth0 看队列丢包数，dropped 列非零说明发送队列满了
  6. 抓包：tcpdump 在各个点抓包对比，看报文在哪一层丢了

六、总结

Linux 内核网络栈的接收路径核心是：

  1. DMA + 中断：网卡直接写内存，中断通知 CPU
  2. NAPI：中断 + 轮询，高负载下减少中断开销
  3. GRO：合并小包，减少协议栈处理量
  4. 协议栈逐层处理：二层 → 三层 → 四层 → socket
  5. Socket 队列：数据放入接收队列，唤醒应用

发送路径核心是：

  1. 应用 → 传输层：构建报文，TCP 做拥塞控制和窗口管理
  2. IP + 邻居：路由查找，ARP 解析下一跳 MAC
  3. qdisc：流量控制和调度
  4. 驱动 + DMA：放入 TX ring，网卡 DMA 发送

性能优化的方向：

  • 并行化：多队列网卡、中断绑定、RPS/RFS/XPS
  • 减少报文数：GRO/GSO/TSO/LRO 大包合并
  • 减少拷贝：零拷贝、分页 skb、分散聚集 I/O
  • 减少中断：NAPI、中断合并、繁忙轮询
  • 内核旁路：DPDK、XDP、RDMA（极致性能场景）

理解了这些，再看任何网络性能问题，都能定位到是哪一层的瓶颈，然后针对性优化。
